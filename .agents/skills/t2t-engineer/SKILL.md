# Engineer TroopToTask changes

Pick the mode that answers the current request. Use [repository operating rules](../../../docs/agents/operating-rules.md), the [retained contracts](../../../docs/stabilization/BASELINE.md#retained-contracts), and the [Definition of Done](../../../docs/architecture/DEFINITION_OF_DONE.md#required-commands) as the source of project gates. A current user request sets scope; this skill does not authorize publication, merge, deployment, messages, or database operations beyond those rules.

- **Understand or investigate:** Trace the user-visible symptom through its route, feature owner, server policy, provider boundary, and relevant history. Reproduce a bug at the cheapest stable surface. Separate observed behavior, source-supported explanation, and inference. Return the smallest falsifiable problem statement and the evidence that would disprove it.
- **Architect or prototype when uncertain:** For a consequential module seam, sketch the caller's use, types, and ownership before implementation. Use a disposable prototype only to settle a real behavior, interaction, or performance fork. Compare observations, choose the simplest shape that preserves retained contracts, and discard the prototype. Routine edits do not need a design arena.
- **Implement a fixed issue:** Pin the required behavior with an existing meaningful test or a focused reproduction. Change the owning code and affected consumers together; remove obsolete paths in the same slice. Prefer a narrow interface and watch request count, payload size, and interaction latency. Add tests for externally specified behavior, including denied paths where relevant, rather than tests that echo the implementation.
- **Verify independently:** State a falsifiable claim, run focused checks, and compare the observed candidate with a valid baseline when making a before/after claim. For UI journeys, use [t2t-verify](../t2t-verify/SKILL.md) and preserve its candidate-bound receipt. Choose one primary affected path and the consequential denied or failure case; widen only when the contract or risk requires it. A separate reviewer can inspect the same claim from fresh source and runtime evidence; independence of execution is useful even when both agents use Astra, but it is not model diversity. Record `PASS`, `FAIL`, or `INCONCLUSIVE` without smoothing over missing evidence.
- **Prepare a PR for review:** Inspect the final diff for intent fit, security boundaries, affected consumers, performance, and unrelated changes. Record required checks and material limits against the exact candidate. Write the PR description around the resulting behavior and give the reviewer a short path through the important files. Ask for findings that identify a concrete failure and evidence, not an exhaustive list of speculative suggestions. Make a concrete, reviewable handoff before any approval question.
- **Close a phase:** Finish its declared acceptance evidence and owning PR before starting the next dependent phase. Keep one current record with the exact candidate and unresolved obligations. A green check on an earlier revision, a missing browser receipt, or an open PR is not a completed phase.

For useful parallel work, the coordinator owns the queue, shared contract, integration, and final verdict. Use at most two bounded workers, each on an isolated branch/worktree and, when driving the app, its own `verify:app --worker 1|2` session. Each brief names one fixed outcome, exclusive files and services, the behavior to preserve, exact checks, and the evidence to return. The coordinator reconciles results against the shared contract before the hard PR boundary; workers do not independently expand the phase or publish overlapping PRs. A short task stays local. The Sol 6 xhigh delegated run on 2026-09-26 is a usable runner in this environment; completion does not depend on Cursor cloud agents, Graphite, or another model family. After a failed check, fix the identified cause and rerun the affected check; persistent environmental failure is `INCONCLUSIVE`, not an endless retry loop.
