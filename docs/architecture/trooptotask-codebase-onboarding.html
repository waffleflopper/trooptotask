Codebase Onboarding Brief

TroopToTask is a single SvelteKit product surface for military unit management. The codebase is organized around an authenticated Organization workspace, feature-owned UI modules, shared client stores, and an app-owned server boundary that keeps business logic away from raw provider calls whenever possible.

Architecture in one pass

Mental Model

A new developer should think in layers. The URL layer gathers context and renders pages. Feature modules own screen behavior. Shared stores carry hydrated Organization data in the browser. Server use cases own business rules. Adapters talk to Supabase, Stripe, storage, and notifications.

Route Files Are Glue

SvelteKit +layout.server.ts, +page.server.ts, and +server.ts files should mostly gather request context, declare authorization, and call feature or server modules.

Features Own Workflows

Feature modules under src/features/* own page views, contexts, stores, read models, and workflow-specific utilities.

Server Core Owns Rules

The strongest current direction is app-owned backend code: entities, use cases, ports, and adapters under src/lib/server.

Application Layer

  • src/routes: URL structure, page loads, form actions, and API endpoints.
  • src/features: feature-owned Svelte components, contexts, stores, read models, and utilities.
  • src/lib/components: shared shell and public-site components.
  • src/lib/components/ui: shared shadcn-svelte and TroopToTask UI primitives.
  • src/lib/stores: shared client-side state and hydration targets.

Server Layer

  • src/lib/server/core/useCases: app-owned business workflows.
  • src/lib/server/core/ports.ts: provider-agnostic interfaces (ports are contracts between core logic and outside services).
  • src/lib/server/adapters: provider-specific implementations for Supabase, Stripe, storage, audit, and notifications.
  • src/lib/server/entities: schema-first table mapping, validation, and audit metadata.
  • supabase/migrations: schema, RLS (row-level security), RPCs, and historical database evolution.

Language first

Domain Vocabulary

The codebase is easier to understand when you use the product's own nouns. The docs explicitly avoid v2 migration language such as Account, Unit, and Element when describing the current v1 system.

Term Meaning In V1 Common Trap
Organization The workspace and tenancy boundary that owns operational data, members, settings, and billing. Do not call it Account, Unit, tenant, or workspace in current-state docs.
Group A configurable roster subdivision inside an Organization, also used for scoped access. Do not casually rename it squad, platoon, section, team, or Element.
Organization Member An authenticated app user who belongs to an Organization. When access matters, do not just say user.
Personnel Record The stored roster record for a person assigned to an Organization. A Personnel Record is not the same thing as a User Account.
Soldier The military-facing person represented by a Personnel Record. Use Soldier in user workflow copy, use Personnel Record for persistence.
Roster Read Model The shared app-side read seam for roster data used across feature surfaces. Personnel owns writes, but many features read roster data.
Feature Lane A permission surface for a product area such as Calendar, Personnel, Training, Critical Tasks, Onboarding, or Rating Scheme. Do not borrow another feature's lane for new behavior.
Policy Decision The structured allow or deny result from membership role, capability, scope, and overlays. Client-side button hiding is advisory only, server decisions enforce access.

Follow the request

Overall Data Flow

There are two common paths to understand first: page reads, where SvelteKit loads Organization and workspace data, and writes, where client stores call Organization API endpoints that are wrapped by policy-aware server helpers.

Read Side

Initial page navigation enters hooks.server.ts, builds Supabase Auth state on event.locals, then the Organization layout resolves the Organization, membership, chrome data, feature workspace bootstrap, and a hydration plan for client stores.

Write Side

User actions usually go through a feature store or explicit fetch, hit /org/[orgId]/api/*, enter handle or entityHandlers, pass a Policy Decision, then call a use case backed by ports and adapters.

Read path

Page Load And Hydration

Workspace pages use SvelteKit streaming where useful. The server returns both feature data and a hydration plan, then the browser-side coordinator loads or merges that data into shared stores.

Request Enters The Server Hook

src/hooks.server.ts creates the Supabase server client, validates the session, enforces MFA flow redirects, rate limits requests, checks suspension, and sets security headers.

Organization Shell Resolves Identity

createRootOrgLayoutLoad and supabaseOrgShell resolve Organization identity, canonical URL slugs, membership access, effective tier, notifications, announcements, and user Organization preferences.

Workspace Layout Loads Feature Data

Feature layouts such as Calendar and Training construct workspace ports, then stream a workspace bootstrap payload through the Organization shell coordinator.

Hydration Planner Names Store Targets

createDefaultHydrationPlanner inspects the workspace payload and creates typed targets for personnel, groups, status types, assignments, training records, Critical Tasks, Rating Scheme, and Onboarding stores.

Client Coordinator Applies The Plan

orgShellHydrationCoordinator replaces or merges store data by snapshot key so shared stores avoid unnecessary reloads and preserve client state where intended.

Write path

Standard CRUD

For simple entity create, update, and delete, define an entity in src/lib/server/entities, then export handlers from an API route with entityHandlers(entity). That gives you validation, mapping, policy, read-only guarding, and audit scaffolding.

Example: src/routes/org/[orgId]/api/training-types/+server.ts

Custom Workflows

When a route does more than normal CRUD, define a RouteConfig with handle(config). The route declares the policy action, optional input schema, and the use case function to call.

Example: src/routes/org/[orgId]/api/onboarding/+server.ts

Patterns to recognize

Code Patterns

These are the patterns a new developer should identify before making changes. The main rule is to keep responsibilities where the codebase already wants them.

Thin Route Shells

Routes gather data, wire contexts, and render feature page views. They should not become the long-term home for feature orchestration or business rules.

src/routes+layout+page

Feature Contexts

Complex feature pages often use a page context or read model to coordinate hydrated stores, filters, preferences, and display rows. Watch for contexts growing too broad.

Shared Stores

The store core supports load, optimistic add/update/remove, batch operations, local replay, and REST adapters scoped to the current Organization.

Schema-First Entities

Entity definitions map snake_case database rows to camelCase app types, define Zod validation, mark group-scoped personnel fields, and attach policy and audit metadata.

Ports And Adapters

Core use cases depend on ports, not raw Supabase clients. Adapters implement those ports with Supabase, Stripe, storage, notifications, and audit behavior.

Access model

Authorization And Scope

TroopToTask v1 now treats member access as a combination of fixed governance role, member preset, capability overrides, scope set, and policy evaluation. Server-side Policy Decisions enforce writes and sensitive reads. Client checks are only user-experience hints.

Durable Feature Lanes

The current durable lanes are Calendar, Personnel, Training, Critical Tasks, Onboarding, and Rating Scheme. Each lane uses capability levels: none, view, operate, and configure.

Scope Sets

Scope is currently either Organization-wide or a list of Groups. Scope limits what a member can reach inside scoped workflows. A future person-level Personnel Scope is documented but not the default current implementation.

Read-Only Overlay

Billing state can place an Organization into read-only mode. Ordinary writes should not bypass that overlay. Only specific recovery paths should use explicit exceptions.

RLS Still Matters

Supabase RLS (row-level security, database rules limiting which rows are visible or writable) remains part of the safety model, but app-layer Policy Decisions are the clearer contributor boundary.

Interface system

UI Composition

The visual foundation is shadcn-svelte with Tailwind v4 and TroopToTask shared components. Route code configures behavior, labels, data, actions, filters, and permissions. Shared components own appearance.

Page Shell

Use ui/page-shell for authenticated page roots, headers, tabs, fact grids, summary rails, and sticky action bars.

Workspace Toolbar

Use ui/workspace-toolbar plus shadcn button groups, dropdown menus, inputs, and selects for route-level controls.

Data-Heavy Views

TroopToTask favors dense tables, matrixes, report workspaces, and summary rails when they help a leader see the whole formation.

Visual guardrail Production routes should not retune shared component spacing, borders, radius, shadows, typography, color, animation, density, or internal selectors. If a shared component does not fit, document the design-system gap and extend the shared component API.

Quality gates

Tests And Governance

The repo uses unit, component, route-adapter, migration, and e2e tests. Governance checks are narrow but important: they keep known architecture drift explicit.

Required Completion Commands

Before implementation work is considered complete, run:

  • npm run format
  • npm run lint
  • npm run governance:check
  • npm run check
  • npm run test

Governance Check Scope

npm run governance:check verifies required governance files, route-level locals.supabase allowlists, deprecated demo or sandbox runtime signals, legacy authorization entry points, and drift-ledger references.

Unit And Component Tests

Most feature modules include adjacent tests for contexts, stores, utilities, read models, and components. This is the default place to prove business-facing calculations.

Route And Adapter Tests

The server architecture exposes pure cores such as handleUseCaseRequest and loadWithContextCore so route behavior can be tested without a full SvelteKit request.

Current-state honesty

Hotspots And Drift

The architecture docs call out drift directly. Do not copy tolerated exceptions just because they exist. Narrow the exception or document it when work touches the seam.

Provider Boundary Leaks

Some routes and utilities still call locals.supabase directly, especially around platform admin, auth, billing, exports, and Organization settings edges. New business logic should prefer use cases and adapters.

Large Orchestration Modules

Calendar, dashboard, duty roster, personnel, training reports, onboarding, and Critical Tasks have areas where contexts or page modules coordinate many concerns. Deepen these deliberately, not as incidental cleanup.

Legacy Terminology

Compatibility names such as clinicRole still exist in schema and code. New docs, UX copy, and abstractions should say Duty Role when that is the user-facing concept.

Historical Surfaces

Leader's Book is retired as an active product surface, while Personnel owns surviving per-Soldier workflows. Demo and sandbox runtime paths should not be reintroduced.

Recommended first week

How To Come Up To Speed

A new developer does not need to read the entire repo first. This path builds the right mental model before they touch production behavior.

Read The Current Contract

Start with CONTEXT.md, UBIQUITOUS_LANGUAGE.md, docs/architecture/ARCHITECTURE.md, MODULE_CONVENTIONS.md, and ADR_INDEX.md.

Trace One Page

Follow one feature from route layout, to workspace port, to use case, to adapter, to hydrated client store. Calendar or Training are good examples.

Trace One Write

Follow training-types or onboarding from UI action to store or fetch, to API route, to handle or entityHandlers, to use case, to Supabase.

Study The Access Model

Read memberAccessShape, policyEvaluator, and routeAuthorization. Confirm whether your feature work needs a read, operate, configure, or governance action.

Use The UI Catalog

Before building route UI, check docs/component-catalog.md and existing shared primitives. Route-level visual overrides are almost always the wrong first move.

Make A Small Vertical Change

For the first real task, prefer a narrow slice that touches one feature surface, one policy action, one use case or entity, focused tests, and the required validation commands.
