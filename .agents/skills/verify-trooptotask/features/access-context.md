# Trusted access and request isolation

An authenticated member's current Organization membership supplies role, feature capabilities and Group scope. The requested route supplies the resource target. Browser fields never supply authority.

## Sub-features

- `allowed-scope`: Organization readers receive their own Alpha, Bravo and unassigned records. Alpha readers receive only Alpha. An explicit empty Group scope receives no people or saved availability.
- `denied-write`: absent or insufficient capability, another Group, an unassigned Person and another Organization cannot authorize a mutation.
- `authority-injection`: actor, role, capability and scope fields in a request cannot elevate a denied caller or retarget the command.
- `fresh-grant`: a request made after narrowing an open page's Calendar grant uses current membership. Reload settles without retaining protected records or an indefinite loading state.
- `removed-membership`: removing an expendable member through Organization settings makes its still-authenticated next A request deny. Its independent B membership and saved A data remain intact.
- `request-isolation`: overlapping requests to different Organizations keep their own target and grant, including requests made by the same account.
- `admission`: a visitor's protected request does not disclose saved records. Normal sign-in and sign-out retain their visible entry and exit paths.
- `private-file-isolation`: Personnel documents and counseling PDFs keep their Personnel authorization. Signed Sign-in Roster scans keep their independent Training and saved-roster scope, including when both use `counseling-files`.

## How to get to it (user POV)

Use Personnel and Calendar from Organization navigation. Use the Organization switcher for an account with A and B memberships. Feature buttons reflect advisory access; an authenticated request to a known target independently checks the server boundary.

## Gotchas

These journeys establish the common request-admission and scope contract through Personnel and Calendar. They do not establish every feature's mutation, private-file, governance, export, job or SQL behavior. When D27 changes a consumer, select its existing feature recipe and repeat its affected allowed/denied, persistence and failure paths. Keep one feature map rather than copying every lane's journey here.

Existing lower-level checks cover membership projection, the six-lane evaluator, empty/out-of-Group matching, identity-owned and governance decisions, request-local membership reuse and rejected-load retry. Read the actual checks before selecting them. Current pointers include `src/lib/access/{memberAccessProjection,memberAccessShape,policyEvaluator,scopeSetAccess}.test.ts`, `src/lib/access/requestMembershipCache.server.test.ts`, `src/lib/access/{policyAdapter,policyAuthorization,policyDenial,routeAuthorization}.server.test.ts` and `src/lib/server/adapters/{requestContexts.server,membershipAdmission,loadWithContext}.test.ts`. Current SQL suites separately protect membership grants, sensitive RPC privileges, tenant/Group row policies and lane independence. Source inspection and passing mocks cannot establish the live database boundary.

For a request-composition cutover, repeat affected persisted edits and denied effects from each changed feature's recipe. Include self-owned notifications/preferences, governance, actual JSON/Excel export inventories, Personnel notes/private-file admission and roster mutation boundaries. Preserve ordinary authenticated HTTP, native interaction and separate provider readback as distinct evidence. Check deferred-load denial and membership-provider error/retry at their stable lower-level boundaries. A request cache reuses one membership snapshot within that request; it does not promise invalidation while the same request is running.

For shared persistence/provider changes, use [Personnel artifacts](personnel-artifacts.md) and [Sign-in Rosters](sign-in-rosters.md) for actual uploads, saved-file reads, removal and allowed/denied scope. Personnel documents use `personnel-documents`; counseling PDFs and roster scans share the private `counseling-files` bucket with separate path and permission rules. A successful roster scan read does not establish counseling access. Counseling has no native download action, so label its authenticated Storage/SQL proof separately. Keep saved rows, exact bytes/hashes and denial witnesses before and after any mutation. An empty removal acknowledgment or provider error cannot establish that an existing object was removed.

`src/lib/server/adapters/persistenceContract.test.ts` exercises the real SDK against finite synthetic responses for Organization binding, Personnel Group filtering before counted pagination, nonempty whole-roster scope, complete provider-sized reads and later-page failure. It establishes adapter transport behavior, not live RLS. Personnel's owned `scopeEnforcement.server.test.ts`, artifact delivery/writer checks and `supabase/tests/{personnel_counseling_file_scope,personnel_sensitive_artifact_reads,sign_in_rosters_rls_scope}.sql` establish their separate boundaries. The old global entities directory and central scope-enforcement adapter are already removed; inspect current owners before reusing older issue pointers.

Classify throttling from its actual owner and storage. The hook's Access-owned `rateLimit.server.ts` Map is process-local and does not provide cross-process durability. Identity acquisition, setup, recovery and password flows consume the separate durable limiter; preserve their database-window and fail-closed contracts. This recipe adds no rate-limit infrastructure or claim of production multi-instance enforcement.
