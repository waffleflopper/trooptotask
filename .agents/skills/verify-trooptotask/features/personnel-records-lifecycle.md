# Manage Personnel records

A member creates and edits a Soldier's record, imports new People or backfills existing dates, and archives or restores a record while keeping its identity, permissions and retained history intact.

## Sub-features

- `record-create-edit`: create through Personnel and Onboarding, edit through the roster modal and detail page, cancel or recover a failed save, and retain the Person ID through name, rank and Group changes.
- `record-import`: upload a roster file, map columns, correct invalid cells, select valid rows, preserve row errors and recover a failed request without claiming an unsaved record.
- `record-backfill`: match active People by rank/name, disambiguate duplicate names by Group, update only supplied ETS/DEROS dates and skip an unchanged replay.
- `record-archive-restore`: single and bulk archive remove People from active views; restore retains their IDs and restores only artifacts archived by that parent event.
- `record-approval`: an operate-only member requests archive approval without archiving the Person; an authorized reviewer applies the archive once.
- `record-access`: view, operate, configure, assigned Group, empty Group scope and foreign Organization requests preserve their distinct permissions and saved data.
- `record-consumers`: Training, Critical Tasks, Calendar, Onboarding and record exports retain the Person identity and their independent access lanes across record changes.
- `record-switching`: Organization changes and late save responses cannot mix A's Personnel or write permissions into B.

## How to get to it (user POV)

Choose `Personnel` in the Organization navigation. Use `Add Person`, a named row's `Edit` or `Details`, or `Import`. On the import page choose `Add new` or `Backfill ETS/DEROS`, upload a file and review the mapped rows before submitting. Archive from the named roster row, its Edit dialog, its detail page, or the roster's `Archive` selection mode. An Organization owner/admin restores records through Settings → `Archives`; archive requests appear under Settings → `Approvals`. The reverse creation path is Onboard → `Start Onboarding` → `Add Person`.

## Gotchas

- Import accepts an uploaded CSV/XLSX file; it has no paste box. Cell edits commit on change/blur and can reset selection, so take a fresh snapshot before submission. Source row numbers include the header.
- Seed the lifecycle bundle once per unchanged scenario. Restore its parent before the next archive; recreate through clean-seeds/reseed or owned worker restart after a replay defect. Never repair proof by editing archived_at directly.
- The seed's archivedDuplicate intentionally remains archived and excluded from matching. Read it by ID; a duplicate-name count alone combines three different states.
- A synthetic pre-request 503 cannot prove recovery after partial provider persistence. Single archive/cascade, review and batch fault boundaries need separate lower-level proof; retain any observed partial effect and its owner.
- Network families personnel, personnel/batch, personnel/merge and personnel/archive-batch match exact A endpoints. Restore every network/feedback/export control, including after failed or blocked attempts. Metadata without stored files cannot prove file download/export cleanup.
- Configure-only Personnel access does not open Organization governance. Use orgOwner/orgAdmin for visible Archives and Approvals; record a member's direct authorized API restore separately from UI reachability.
- Preserve focused lifecycle, batch, merge, archive-artifact, slug, modal/import/detail/store and denied-route tests. `supabase/tests/personnel_unassigned_row_scope.sql` and `personnel_artifact_rls_group_scope.sql` provide distinct isolated provider/security proof; browser/API checks do not replace them. Existing component tests cover async modal failure and import selection/date validation below the browser.
- Restore original fixture fields through the app, dispose of UI-created temporary People visibly where authorized, then clean only helper-created seeds and run owned cleanup. Pending requests or packets may require owned restart/cleanup; no broad helper deletion is implied. Confirm durable evidence survives cleanup.
