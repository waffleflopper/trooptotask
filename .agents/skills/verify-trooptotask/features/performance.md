# Performance measurement on seeded workloads

A leader opens the Calendar, Personnel, the Organization Dashboard, a report or an export for a platoon-, company- or battalion-sized unit, works in it, and waits for each step to be usable. This recipe measures those waits reproducibly: three deterministic synthetic Organizations, an Organization-wide actor, a Group-scoped operator and a Group-scoped editor, one journey registry, a fixed cold/warm protocol, and request, byte, main-thread, server-timing and query evidence for every sample. It measures; it does not classify or fix.

## Sub-features

- `workloads`: `seed workload small|typical|large` creates one synthetic Organization of 20, 100 or 400 active People from the declarative table in `helpers/perf-workloads.mjs`, journaled before any write. `clean-seeds` removes exactly those rows, plus the rows the app wrote while the workload was driven (audit rows survive Organization deletion, so they are journaled and removed by ID first), and reads every ID back.
- `load`: repeated page loads, each timed to three points. `firstUsefulRenderMs` is the journey's milestone. `settledIncludingReloadsMs` is the later of that and the end of the last app document or data response, read once the app origin is idle. `documentCompleteMs` is when the page's own document response ended (navigation `responseEnd`); a streamed document can end long after the render. Each sample records a Resource Timing manifest grouped document/JS/CSS/data/provider/other. The manifest counts resource entries, network requests (entries that transferred bytes) and cache hits separately, with transfer, encoded and decoded bytes, each entry's response status and `x-sveltekit-invalidated` bits. Failed requests come from the native network list. Each sample also records navigation, paint and LCP (loads only: an interaction sample omits them, because they describe the preparation page load), long tasks, the matching server timing lines per load and its own pg_stat_statements window.
- `journeys`: one declarative registry in `helpers/perf-journeys.mjs`. Each journey names its page, the actors it applies to (with the reason for any it does not), load or interaction, read or write, its untimed preparation steps, its one timed trigger and the milestones the observer waits for. A milestone can wait for texts, selectors, the text inside an element, an exact element count and a file download. The last milestone is the first useful render; earlier ones, such as the Dashboard's deferred summary or the Personnel detail header, are reported as their own points.
- `interaction`: an input-to-settled timer with the same two points. It opens the journey page, waits for its ready milestone and idle, runs the preparation steps, waits for idle again, then arms the observer and runs the trigger. The observer starts at the first trusted input event. A milestone's time is `performance.now()` read inside the first animation-frame callback that finds the milestone in the page, minus that event's `timeStamp`, on one timeline. A useful point is therefore when a frame that already holds the result begins its work, and that frame paints it next. The callback's own frame timestamp is not used for interactions: it is the frame's start, which can precede the input the frame handles and gave negative times in D01 r4. A load keeps the frame timestamp, measured from navigation start. Every step is a native click, hover, fill, type, key press or file upload on a control named in the accessibility snapshot, never an app handler. The query window opens just before the trigger, after the page's document has ended. Its `documentCompleteMs` is that document's end, measured from its navigation, before the input.
- `trace`: one cold traced load to network idle, the raw `.json.gz`, the native insight text and a compact summary (first useful render, idle, failed requests, FCP, LCP, main-thread busy, scripting, style/layout/paint, long tasks and blocking time after first paint). Hydration is reported as not identifiable because the app emits no hydration mark. V8 keeps the cold sign-in script's source, so the raw trace is written to `.verification/perf-raw` (the one place beside the evidence root the browser tool may write), the actor's password is replaced with `<redacted>` in the copy saved under the evidence root, and the raw file is deleted even when the trace fails. A trace that fails after it started is stopped.
- `statements`: reset or read the owned database's pg_stat_statements, top N by total time and by calls, plus a per-role total. Each role total also counts `plannableCalls` (every statement but `BEGIN`, `SET` and `COMMIT`) and `plans`. PostgREST plans its `set_config` preamble as `authenticator` and runs it as the request role, so those plans land on an `authenticator` row with no calls. Under the pinned regime the plans of the request roles plus `authenticator` equal their plannable calls (31,216 of 31,216 over the D01 r4 run); fewer plans there means some executions reused a generic plan.
- `prepare`: waits 11 s for the seed's row counts to reach the cumulative statistics, then runs `VACUUM (ANALYZE)` on exactly the 20 tables a workload seed writes (`PERF_PREPARED_TABLES` in `scripts/verification/environment.py`): the Auth users and identities, the Organization and the workload tables. It then pins the plan regime. It sets `plan_cache_mode = force_custom_plan` on the `authenticator` role that PostgREST logs in as and turns on `pg_stat_statements.track_planning`. It restarts the owned PostgREST container, so every pooled connection logs in after the setting, and waits for its schema cache. `seed workload` runs it after its inserts, reports its time as `timingsMs.prepare` and returns the readback as `planCache`. `perf tables` reads those tables' live and dead rows, visible pages and vacuum/analyze counters, plus the plan regime. The regime readback takes three facts from the database: the role setting, a fresh login as `authenticator` switched to `authenticated` as PostgREST switches it, and how many PostgREST connections (`pg_stat_activity`, application `PostgREST 14.10`) opened before the pin. It is `pinned` only when the setting and the login read `force_custom_plan` and no connection predates the pin. Every run records both reads before its warm-up and after its last sample. It lists in `tables.maintenance` each table a vacuum or analyze touched in between, and in `tables.planCache` both regime readbacks. A run does not start on an unpinned regime.
- `explain`: `EXPLAIN (ANALYZE, BUFFERS)` for one named statement from the fixed registry in `scripts/verification/environment.py`, run as the workload actor with RLS applied. There is no arbitrary SQL. The registry binds literal values, so PostgreSQL plans each explain for those values, the same plan the pinned regime gives a parameterized request.
- `summarize`: one Markdown and JSON table over every run file in a run directory, plus a table of statements per request-path category (Auth, PostgREST setup, session RPC, suspension RPC, `organizations` identity and admission reads, memberships, the page's own reads).

## How to get to it (user POV)

A member signs in, chooses the Organization and lands on its Dashboard, or opens Calendar or Personnel from the sidebar. The Organization owner sees every Group; the scoped member sees only the first Group. The interactions are the ones a leader repeats: changing the Calendar range, searching, saving an assignment, opening and editing a Person, importing a roster, switching Organization and exporting.

## Driving it with verify:app

Launch and drive under Node 24 (`mise exec node@24 --`); the adapter refuses newer Node. Set `V="mise exec node@24 -- node .agents/skills/verify-trooptotask/helpers/control.mjs --worker $WORKER"` and `RUN=.verification/evidence/verify-trooptotask/<run>`. `$V perf --help` prints every command.

1. Seed: `$V seed workload small`, then `typical`, then `large`. Record the returned counts and `timingsMs`; they are the seed timings, and `prepare` is the vacuum and analyze that ends each seed. The workloads share tables, so the last seed's preparation covers every workload. The returned `actors`, `sentinels` and `searchTerms` are what the observer waits for.
2. Sign in once per actor: `$V actor perfWide personnel large`, `$V actor perfScoped personnel large`, `$V actor perfScopedLeader personnel large` and, for `admin-users`, `$V actor platformReviewer admin/users`. Each perf actor is a member of every seeded workload, so the same page drives all three. Keep the returned page IDs. The control records which actor each page was signed in as; a warm `perf load` or a `perf interaction` rejects a page whose actor differs from the ACTOR argument, so a scoped label cannot record a wide page. Cold samples create their own page for the named actor.
3. Load: `$V perf load PAGE WORKLOAD JOURNEY ACTOR --mode cold|warm --out $RUN`. `--out` is checked before any sample and `--reps` must be at least 1. Warm defaults are one warm-up and five repetitions, unthrottled; cold defaults are three repetitions and apply only to `calendar-initial`, `personnel-list` and `dashboard`. Run warm before cold so the server is warm. Add `--profile slow-cpu` for a 4x CPU slowdown.
4. Interaction: `$V perf interaction PAGE WORKLOAD JOURNEY ACTOR --out $RUN`. `organization-switch` needs a second seeded workload to switch from.
5. Trace: `$V perf trace PAGE WORKLOAD JOURNEY ACTOR --out $RUN`.
6. Queries: every measured sample of `perf load` and `perf interaction` resets pg_stat_statements and reads it back. A load resets after its setup (a cold sample's sign-in) and immediately before navigation. An interaction resets after the page is ready, idle and its document has ended, immediately before input. Each read happens at network idle and after the sample's document has ended, so a streamed document's server work lands in its own window. The run keeps each sample's per-role totals and the top 15 statements summed over the measured windows, with calls per window. Warm-ups open no window. `$V perf statements reset|read --top N --out FILE` does the same by hand. `$V perf explain NAME WORKLOAD wide|scoped --out FILE` explains one registry statement as that actor.
7. `$V perf summarize $RUN` writes `summary.md` and `summary.json`. It reads every run file below `$RUN` except `superseded/` and its own `summary.json`; the superseded runs it finds are listed apart as diagnostics, never in the run tables. Redirect its console output outside `$RUN`; an empty output file inside it fails the parse.
8. Close out in this order. Run `$V clean-seeds` and save its readback, which must show 0 remaining rows and accounts for every workload. Save a final `npm run verify:app -- doctor`. Run owned cleanup with `npm run verify:app -- cleanup` and confirm the run directory survived. Then package the run as one archive by the [artifact packaging](../../../../docs/architecture/DEFINITION_OF_DONE.md#packaging-durable-artifacts) rule, re-extract it into empty scratch space and verify the inventory. The coordinator uploads it.

### Workload shape

| Workload | Groups x People | Archived | Window | Status / duty (Calendar lanes) / Training types | Critical Tasks | Onboarding active / done | Extra members admin / member |
| -------- | --------------- | -------- | ------ | ----------------------------------------------- | -------------- | ------------------------ | ---------------------------- |
| small    | 2 x 10          | 10%      | ±90 d  | 4 / 2 (2) / 8                                   | 10             | 2 / 2                    | 1 / 2                        |
| typical  | 5 x 20          | 10%      | ±90 d  | 6 / 4 (3) / 15                                  | 25             | 5 / 10                   | 2 / 8                        |
| large    | 16 x 25         | 10%      | ±90 d  | 8 / 6 (4) / 25                                  | 40             | 20 / 40                  | 4 / 30                       |

Every workload has about one availability entry per Soldier per 30 days, one daily assignment per duty type per day, 85% Training completion, and 60% Critical Task completion with 25% older history. The sizes come from Robert's 20/100/400 Personnel decision. Groups are platoons or sections, so no workload puts one giant Group in front of the roster. The roster carries about a tenth archived history. Members are the unit's leaders and admin staff, not every Soldier. The anchor is the fixture's operational day, so dates move with the run while IDs, names and proportions stay identical.

The Calendar reads a few more rows per Organization. Every status type carries the short label the Calendar shows. The first duty types are Calendar lanes, the duties a unit watches on the month (Staff Duty and CQ, then Runner, then Detail Group), and the others stay planner-only. Every workload has the same 105 special days, because a unit's holidays do not scale with its size: the 11 federal holidays of each year from the anchor year minus 1 to plus 2 (the years the Calendar reads), a training holiday on the Friday beside each Monday or Thursday holiday, and ten weekdays of holiday block leave from 22 December. About 17 of them fall inside the ±90-day window.

`dashboard-navigation` is the Dashboard's measured input: the Dashboard renders no in-page link and its `+N more` toggles appear only from typical (the scoped actor has no Out Today at large), so the sidebar link is the one control present in every cell. The Dashboard's lists already name roster People, so the roster text alone is met before the route changes; the breadcrumb is what only the Personnel page shows. Its load-to-usable total is the `dashboard` load's `useful` plus this interaction, which starts only after the Dashboard is useful and idle.

`perf --help` lists the registry with each journey's kind, effect and actors. The ordinary page GET of the request path is the `personnel-list` warm load; `sidebar-navigation` is its client navigation.

`perfScopedLeader` is an Editor scoped to the same Group as `perfScoped`, a role Settings Members can assign. The Training briefing detail is the affected-soldiers section below the report. Each open and each page is one `/api/training-reports/detail` request. The Calendar report UI caps no range: its date pickers accept any span. The longest preset that holds workload data is the current calendar year, the Status days default, so `calendar-report` measures that. Rows outside the ±90-day workload window are empty, so a longer custom range adds no server rows; only the two by-day modes expand per day in the browser.

`members-list` and `organization-export` need Organization settings, which the Group-scoped operator cannot open (403). `admin-users` is the platform user directory, the largest list the product shows: it spans every Organization, so its size is the whole owned Auth directory at the time of the sample. Seed the workloads one at a time and measure it after each seed to see it grow.

### Protocol

- `cold`: each sample opens a new isolated browser context on a static image and signs in by posting the real login form action, which runs no app code. It then navigates to the journey and closes the context once the sample is read. Route chunks, page data and the document are uncached. The shared entry CSS and JS are cached, as for any visitor who arrives through sign-in; the manifest counts them as cache hits. Defaults: no warm-up, three repetitions.
- `warm`: each sample navigates the signed-in actor page to the journey URL after the warm-up. It is a new document with the HTTP cache kept.
- Each journey's milestones are in the table above and in the registry. The Dashboard shows only its own skeleton until both the streamed bootstrap and the deferred summary resolve, so `summary` is when the summary arrived and `useful` is when the panels finished rendering.
- Every sample then waits for app-origin network idle: no request pending in the native network list, no answered fetch still streaming its body, and no new request or Resource Timing entry for 500 ms. The manifest and settled time are read there. The sample then waits for its document to end, and only then are server lines and statements read and a cold context closed. One cap of 120 s bounds each wait: the useful render, idle, the document's end and each preparation `wait`. A sample that never idles reports `networkIdle: false` with the paths still running, and no settled time. A document still open at the cap is reported as `documentOpen: true` with `documentOpenMs`, and the next sample starts only after it ends (or the run stops after a second cap).
- Order: seed every workload the run measures, each seed ending with its preparation, before the first sample. Then run each journey as one warm-up and its samples. Run read journeys before write journeys, and `personnel-import` last, because writes leave dead rows and modified-row counts that can start autovacuum or autoanalyze. `organization-export` may run among the reads: it writes only export history and audit rows, which no other journey reads. After `clean-seeds`, reseed in the same order. A read journey whose run lists `tables.maintenance` is rerun after `perf prepare`.
- Plan regime: every comparison run uses custom plans (`perf prepare` pins them). PostgREST sends each read as a parameterized prepared statement on a pooled connection. In PostgreSQL's default `auto` mode the first five executions on a connection use custom plans; then PostgreSQL may switch the statement to a generic plan when that plan's estimated cost is not much higher than the average custom-plan cost (PostgreSQL 17 `PREPARE`). Which plan a sample got would then depend on the history of the connection it landed on. Custom is deterministic, and it is what every production connection uses for a statement's first five executions. A long-lived production connection may move a statement to a generic plan, which this protocol does not measure.
- Host gate: each measured sample starts only on a clear host and is watched while it runs (`helpers/perf-host.mjs`). It reads the 1-minute load every 2 s, and the CPU time of every build, test or verification process (Vite, Vitest, `node --test`, `python3 -m unittest`, svelte-check, Playwright, ESLint, Prettier, tsc, another verification daemon or browser) whose command line and working directory lie outside this checkout and its verification state. A sample is contaminated if the load exceeds 4 at any reading, or those processes use 25% of one core in any tick. Across the D01 r3 run, 95% of readings with no such process stayed at or below load 2.5 on this 16-thread host. A contaminated sample is kept out of the distribution, recorded in the run's `rejected` list with its verdict and measured again. More than five stop the run, and the error names every rejected attempt with its reasons. In the D01 r4 run, three runs stopped this way while another checkout ran its full check and verify app; each was measured again once the host stayed clean for 10 minutes. Each kept sample records its `host` verdict with its wall-clock span. A write journey that alternates on the sample index (`toggles`) runs one more unmeasured sample when rejections leave an odd count, so it still ends as seeded, also when the run stops.
- Host build: each run file and trace summary records `host` with the running browser's build and DevTools protocol, read from the owned browser's `/json/version` (the HTTP form of `Browser.getVersion`), and the kernel release. `perf summarize` repeats it on every row. The doctor's `browser.version` is the binary's version at launch, so it misses a package upgrade under a live browser.
- Comparison rule: a baseline cell is dated classification evidence for the browser build and kernel it ran on. A repair compares a before and an after measured on one recorded environment: the same browser build and kernel, on the repair branch's merge base, prepared and pinned the same way. A baseline cell serves as the before value only when it ran on that same build and kernel and the merge base leaves its journey's code paths unchanged; otherwise the repair measures its before first. A bridge does not make two environments equivalent. In the D01 r6 run, a system upgrade moved Chromium from 152.0.7977.82 to 154.0.8037.97 and the kernel from 7.2.5-3 to 7.2.8-9 between two halves of one run. A bridge of one cell per kind kept for classification each earlier kind whose bridge median stayed inside its earlier range. Inside the range, Calendar initial still moved 12.8% (1676 to 1462 ms), and single SQL paths can move while a page holds steady. Bridged cells therefore classify; they are not before values on the new build.
- Report min, median, max and every sample. With five samples, a p95 would be a guess; do not report one.

## Gotchas

- A reload never gives a cold load. Chrome serves the content-hashed `/_app/immutable` assets from cache on every reload, including `navigate_page` with `ignoreCache`, and the native tools have no cache-disable control. That is why `cold` uses a fresh context. The fresh context cannot start with an empty cache either: the image page requests `/favicon.ico`, the app redirects it to `/auth/login`, and Chrome follows that page's `Link` preload headers for the shared entry assets.
- The app rate-limits by IP (`src/lib/access/rateLimit.server.ts`): 10 `/auth/` POSTs per 15 minutes, 10 Organization exports per hour, 30 Organization API writes per minute and 60 other requests per minute. Every sample comes from loopback, so samples start at least 6 seconds apart per worker, cold sign-ins wait for a slot (8 in any 15 minutes), roughly two minutes per cold sample once the budget is spent, and an export sample waits for one of 10 slots in any hour. Six export samples per workload therefore span about two hours over three workloads; run other journeys meanwhile on another page. The rest of the journeys are warm only because of the sign-in limit. When a budget runs out anyway, doctor reports `APP_ENDPOINT_UNAVAILABLE`, because its `/auth/login` probe gets a 429, or a cold sample reports `Cold sign-in returned failure`. Sending a captured session as a request header does not work: the first post-hydration invalidation is answered signed-out.
- Above 250 People the By Group roster shows `Grouped roster paused` instead of rows. A large wide `personnel-list` sample therefore settles on that notice and renders no Person rows; compare it with large scoped and typical wide, not as a like-for-like row count.
- `$V server-source arm TABLE hold` matches only a GET to `/rest/v1/TABLE` whose single query parameter is `organization_id=eq.<Organization>`. That holds `rating_scheme_entries` and `personnel_ict_completions` for a Person detail open, while `availability_entries` and `personnel_trainings` report `matches: 0` and the lane resolves unheld. Read `matches` in `server-source state` before counting a hold as a delay. The deadline runs from the arm, so a lane resolves earlier than `HOLD_MS` after the click by the seconds between arm and click (5.0 s after the click for an 8 s hold clicked about 3 s after arming); `server-source release` resolves it on demand.
- Only Calendar, Dashboard and Training emit `[*-load]` server timing lines. A Personnel sample has none; use its statements and `responseStartMs` for the server side.
- pg_stat_statements covers the whole owned database for the window, including auth and PostgREST setup statements. Read `byRole` before attributing time to the app.
- The explain registry is shaped like the app's reads, not copied from them. Use pg_stat_statements for what the app actually ran and explain for why one statement costs what it does.
- Restart recreates fixtures and loses workloads. Reseed and sign in again after every helper edit, because doctor reports `STALE_CANDIDATE` until restart.
- Local unthrottled numbers show relative cost and request shape, not field latency. Record the host's CPU and load alongside them.
- There is no network emulation. Chrome refuses network throttling while the daemon's owned-origin URL allowlist is set, and that allowlist stays. Field network latency is not measured here.
- A first visit has no viewer time zone cookie, so the root layout sets it and calls `invalidateAll()` on mount. Every cold sample therefore reloads all page data right after the first render; on a Dashboard that reruns the summary load at the same time as the document's. Server timing reports each load and the loads per sample; never add them up as one wait. `settledIncludingReloadsMs` is where that reload ends.
- The native network list shows a status as soon as response headers arrive, and a streamed `__data.json` keeps its body open after that. Idle therefore also compares answered fetches with finished Resource Timing entries.
- Idle does not see a document that is still streaming, because an open document adds no Resource Timing entry; its navigation `responseEnd` stays 0 until it ends. The Critical Tasks layout streams its workspace on every child route, so the large wide report's document stays open about 47 s after the report is useful. The server keeps running a stream after the browser navigates away, so each sample waits for `documentCompleteMs` before its window closes and before the next one opens. A perf navigation returns at the page's load event within the cap, so a load sample is read after its document ends: the manifest holds the whole document, and `settledIncludingReloadsMs` includes its end (46.8 s for that report in D01 r4). Before the cap reached navigations (`bd4a4c898`), the read came at idle while the document was open: the r2 run recorded 300 document bytes and settled 3.1 s for the same report.
- `vite preview` compresses every response with `@polka/compression` (`node_modules/vite/dist/node/chunks/node.js`, Vite 8.0.16), and it never flushes a streamed write. A streamed document or `__data.json` therefore reached the browser only once about 16 KB of compressed output existed or the stream ended: the large scoped Dashboard document answered headers at 43 ms and delivered all 73 KB in one chunk at 3.4 to 4.5 s. The owned preview loads `scripts/verification/preview-streaming.mjs`, which asks app responses for identity encoding, so they stream as production does; `/_app/immutable/` assets stay compressed. Document and data transfer bytes are therefore uncompressed sizes. Runs before this change (the r1 D01 archive) carry the compressed behavior. Production delivery is not measured here.
- `navigate_page` keeps its `initScript` only until the call returns, and its default navigation timeout is 10 s. A document that commits later, such as the large wide Training report (about 28 s to first byte), would load without the observer and report nothing useful. Perf navigations and preparation `wait_for` calls therefore pass the 120 s cap as their own `timeout`; the daemon gives a call that names a timeout 5 s more than it, and 45 s otherwise. A timed-out `wait_for` reaches the control as an error, not as text. Page evaluations cannot name a timeout, so the settled reads poll in 20 s calls.
