# Verify TroopToTask in a browser

Use the repository's `npm run verify:app -- <command>` entrypoint. It builds a production-mode copy of the current candidate, starts a new disposable local Supabase project with synthetic users, and owns its Chrome session. It does not attach to an arbitrary URL, browser profile, or provider. Read [the initial feature map](references/feature-map.md) when choosing a journey or updating selectors.

1. Read the [verification contract](../../../docs/architecture/DEFINITION_OF_DONE.md#computer-use-flow-evidence) and run `npm run verify:app -- info`. Use `setup` if `info` reports no compatible Chrome. Inspect `npm run verify:app -- --help` for the current command surface before driving.
2. Run `npm run verify:app -- launch` and then `npm run verify:app -- doctor`. A `PASS` doctor identifies this worker's app origin and executable candidate. After an unexpected browser or provider result, doctor again; if the candidate changed, use `restart` before collecting new proof. Worker `1` is the default; `--worker 2` is available for one independent, exclusive session.
3. Drive the user path. `login manager|viewer|scoped|foreign` signs in through the visible form. `tools` lists native DevTools names and schemas; `tool NAME '{...}'` exposes snapshots, interaction, console, network, screenshots, and traces. Get a fresh `take_snapshot` before choosing an element UID. Use the returned `pageId`; do not guess from tab order. `mcp` exposes the same owned worker as a stdio MCP server when the client has registered it.
4. For the mapped contracts, run the relevant `prove group-persistence|group-authorization|personnel-scope`. The command returns `PASS`, `FAIL`, or `INCONCLUSIVE` and writes a receipt under `.verification/evidence/`. `check-receipt FILE` rejects a stale, negative, or deliberately mutated receipt. The receipt proves only its named claim; retain raw observation, expected outcome, candidate, role, scope, and redacted browser evidence required by the owning task. One representative user path and its consequential denied or failure state are enough for an ordinary focused change; expand only for its actual risk and acceptance criteria. Never turn an unavailable journey into a pass.
5. Run `cleanup` for the worker you launched, including failed attempts. It stops only owned app/browser/provider resources and retains evidence. Do not publish private session files, credentials, raw tokens, or unreviewed screenshots.

The CLI returns exit code `0` for success, `1` for a behavioral failure, and `2` for blocked or inconclusive work. `launch --mutation persistence|authorization` is a disposable negative control; its receipts cannot approve healthy code. Repository tests, the full candidate checks, database checks, and release gates remain governed by the [Definition of Done](../../../docs/architecture/DEFINITION_OF_DONE.md#required-commands). Never operate a remote database or reset an existing local one.

When maintaining this skill, check each mapped area against its current route, policy, and fixture source, then drive it once on the owned app. Classify a mismatch as a product regression, feature-map drift, or harness drift before editing. Keep maintenance edits within this skill and `scripts/verification/`; report product regressions to their owning task. Update the map and harness in the same PR as a feature change that makes them stale. Finish when the affected paths have current source and live evidence or a named blocker; no scheduled audit, exhaustive leaf tour, or repeated retry loop is implied.
