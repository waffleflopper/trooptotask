### PR 1 set-based Calendar read scope and the scoped save

**Repaired and measured; PR 2 made the client repairs (below).** Refs [#1710](https://github.com/waffleflopper/trooptotask/issues/1710). The three D06 bottlenecks at large wide spent their time in per-row RLS helpers on the two Calendar tables. One migration removes that cost and changes no application code. At large wide the warm Calendar settles in 180 ms instead of 1539, the current-year status-day report in 279 ms instead of 2356, and the confirmed assignment save in 112 ms instead of 1319. Every budget passes for both actors, and no other cell regresses past its class. Report rows and totals, Calendar rows and live access are identical before and after. The hosted speedup arrives only when the owner applies the migration ([RELEASE](RELEASE.md#phase-12-d06-set-based-calendar-read-scope)). The application works with or without it.

- **Cause.** The `availability_entries` and `daily_assignments` SELECT policies called `can_view_availability_record` and `can_view_daily_assignment_record` for every row the index scan returned. Before EXPLAIN at large puts that at 0.285 ms per row. Availability took 683 ms for 2400 rows and assignments 307 ms for 1086 rows. The save RPC's check `can_replace_daily_assignment_rows` and its `DELETE` matched the Organization's rows through an `OR` with a correlated `jsonb_to_recordset`, so both ran `can_edit_daily_assignment_record` across every assignment row the Organization had. Before EXPLAIN at large puts the check at 330 ms and the whole save at 1008 ms for one slot.
- **Repair** (`d20106f52`). [`20261020000600_set_based_calendar_read_scope.sql`](../../supabase/migrations/20261020000600_set_based_calendar_read_scope.sql) admits an availability row when its `(organization_id, personnel_id)` pair is in D04's `member_access_private.viewable_personnel('calendar')`. It adds `calendar_private.viewable_assignees()`, the `(organization_id, assignment_type_id, assignee_id)` triples the caller may view, and admits an assignment row whose triple is in that set. A Person assignee comes from the same `viewable_personnel('calendar')` set under a Person type, and a Group assignee from Group scope under a Group type. PostgreSQL computes each set once per statement as a hashed SubPlan. Both policies now apply to `authenticated` only, and anon had no visible rows before. The two replaced helpers had no other caller in migrations or application code and are dropped. The save's check and `DELETE` gain a leading `date = ANY(...)` over the replaced days and the slots' days, which the date index uses. The days, locks, lock order, errors and results are unchanged. Signatures and grants are unchanged.
- **Not changed.** The availability duty lookback, the reload-anchor cookie and the cold double load are client work for PR 2. This PR measures them as PR 2's before values (Client work left, below).

Reloading on December showed October, read the July–September prefix again (243397 B at large wide) and rewrote the cookie to October. **Repair.** The store opens on the first of the cookie's month, and moving months writes the cookie from the store. `Today` writes the current month, and `Open in calendar` on Person detail moves the store to today. The cookie keeps its 30-day `Max-Age` from the last move.

Every cold Calendar sample ran its workspace bootstrap twice. **Repair.** The layout invalidates only `app:viewer-day`, which the loads that read the viewer's day now declare: the Dashboard, onboarding, Personnel detail and its tabs, and the Training and Critical Tasks reports. Each of those loads has a load test that records `depends` with `app:viewer-day` and asserts a literal result for a viewer behind UTC (`6adc31a1f` replaced a source-text scan).

### PR 1 streamed-response session refresh

**Repaired and proven live; the speed repair is not in this PR.** Refs [#1708](https://github.com/waffleflopper/trooptotask/issues/1708), found defect "streamed responses crash the server through `cookies.set`". A streamed load kept using the request's Supabase client after SvelteKit had generated the response. When the access token reached auth-js's 90 s refresh margin, the refresh called `cookies.set`, which throws then, and the unhandled rejection exited the Node process.

- **Prevention.** `readIdentitySession` (the Identity transport edge) refreshes the verified session before the response when it expires within 390 s: auth-js's 90 s margin plus a 300 s stream allowance. The rotated cookies ride the response headers, and a stream shorter than the allowance never refreshes. A failed refresh follows the existing stale-session handling (`STALE_SUPABASE_AUTH_ERROR_CODES`, cookies cleared, anonymous). Any other refresh error keeps the still-valid session. A fresh session adds no provider call.
- **Guard.** `createAuthCookieWriter` (`authCookies.server.ts`) writes provider cookies until `handle` marks the response generated, then drops them and logs one `[auth-session] { event: 'cookies_dropped_after_response', count }` warning with no names or values. The hook wires it and marks the response in a `finally` around `resolve`. A stream that outlives the allowance survives.
- **Allowance.** The repository sets no function `maxDuration` (`svelte.config.js` uses the default `adapter-vercel()`, `vercel.json` has no `functions`). 300 s is the default function duration Vercel documents (not verifiable from this repository), so it is the longest invocation the code assumes. The hosted limit and the hosted JWT lifetime are unknown external settings; local `supabase/config.toml` uses 3600 s. A hosted lifetime at or under 390 s would refresh on every request.
- **Limit.** A stream past the allowance still drops its one rotation, and the browser's refresh token is then consumed under `enable_refresh_token_rotation = true` with a 10 s reuse interval. The browser's next request after that interval presents a revoked token, and GoTrue can then revoke the session family and sign the user out (inferred from the configuration, not reproduced). Prevention makes this require a stream longer than the allowance, or an early refresh that failed at the provider: a retryable outage keeps the still-valid session rather than failing the request, and if the provider recovers before a stream crosses the 90 s margin, that rotation is dropped the same way. It is not removed.

**Tests** (`src/hooks.sessionRefresh.test.ts`, the real `@supabase/ssr` and auth-js client against a stubbed provider that rotates refresh tokens, plus `authCookies.server.test.ts`): a fresh session makes no refresh call and sets no cookie; a session 290 s from expiry refreshes once before `resolve`, sets `sb-refresh-auth-token`, and the next request authenticates on `refresh-1` with no second refresh; an early refresh that meets a provider outage (503) keeps the still-valid session and sets no cookie; a refresh made after `resolve` through PostgREST completes, sets no cookie, logs the exact warning once and leaves no `unhandledRejection`. Without the repair the near-expiry case fails (no refresh is made) and the after-`resolve` case fails with the `cookies.set` throw from `applyServerStorage`; the fresh and outage cases guard behavior that already held.

**Live proof.** `verify:app` worker 2, Chromium 154.0.8037.97, Node 24.22.0, `dashboardView` Home from Calendar with `server-source arm ict_tasks hold 1 100000`, which delays the Critical Tasks summary's catalog read so its next read dispatches near the end of a 150 s token. **Plan regime.** PostgREST runs each read as a prepared statement on a pooled connection. In PostgreSQL's default `auto` mode a connection uses custom plans for a statement's first five executions and may then move it to a generic plan, but only when the generic plan's estimated cost is not much higher than the custom plans' average. `perf prepare` pins one regime: it sets `plan_cache_mode = force_custom_plan` on the `authenticator` role, turns on `pg_stat_statements.track_planning`, restarts PostgREST and reads the setting back through the request path. Every run records that readback before and after, and an unpinned run does not start. All 113 r6 runs were pinned before and after, and their windows hold 18,588 plannable app executions and 18,588 plans (`analysis/regime.md`); r4's 125 runs held 31,216 of each. Production's `auto` mode can move a long-lived connection to a generic plan, which D01 does not measure.
