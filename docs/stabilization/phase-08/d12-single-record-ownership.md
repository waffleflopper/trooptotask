## Delivered boundary and behavior

Personnel's server entry now supplies the mapper and named create/update operations. All ten mapper callers, the detail loader, request-adapter test and staged provider probe use its owner. The old mapper/slug files and entity export are removed; the central lifecycle factory no longer implements create/update. The remaining central batch/merge/readiness consumers use the owned mapper/slug helper. They are not accepted as fully migrated operations by this PR. PersonnelOnboardingEntity belongs to D15 and is unchanged.

A create/rename can collide with a Person hidden by ordinary Group visibility. Previously each retry regenerated that same occupied URL. Remember only candidates rejected by the existing unique constraint and combine them with the permitted read result on the next attempt. This preserves sequential suffixes, bounded retries, ordinary request-user persistence and visibility, without privileged reads, additional requests, broader grants or schema changes.

Personnel and Onboarding now assess Add Person against the member's actual Organization/assigned-Group scope. Creation lists only permitted Groups; assigned-Group creators must explicitly choose one and cannot clear it or choose unassigned. Empty scope has no creation control. Edit choices retain their existing policy and behavior. The portable creation-resource function has three current consumers, including optional Onboarding rank bootstrap. The server separately authorizes the submitted Group. Onboarding uses Personnel's public Web component and narrow create command instead of its private mutable store.

An Organization switch can legitimately make that command return no confirmed Person. Onboarding now rejects that result before its shared form reports success or closes, with a reload instruction. This does not claim the old Organization's write failed or change the store's stale-response protection.
