# Manage Personnel artifacts

A member records follow-ups and leader notes, uploads counseling PDFs and other documents, and manages each Soldier's retained history through archive, restore, export and scheduled retention.

## Sub-features

- `artifact-entry-points`: the Personnel Overview previews and the Log, Files and Archived tabs retain the same Person identity.
- `artifact-create-retry`: failed saves retain text, dates and selected files; visible retry creates one saved artifact and reload shows its submitted fields.
- `artifact-follow-ups`: create and edit title, notes and due date; complete, reopen, archive and restore while retaining the saved identity.
- `artifact-counseling`: upload a completed session's PDF, conducted date, title and optional summary without adding signature tracking or a counseling form workflow.
- `artifact-documents`: upload supported files within the file and per-Soldier storage limits, derive or edit the title, and open the authorized saved file.
- `artifact-notes`: create and read the accepted leader-note shape, preserve contributor-label fallback and archive/restore behavior.
- `artifact-lifecycle`: archive individual items, restore or permanently delete them from Archived, and retain the parent archive event and unrelated historical items.
- `artifact-sensitive-scope`: distinguish configure reads from operate writes, authorized Alpha from Bravo/unassigned/empty scope, and the requested Organization from a foreign Organization.
- `artifact-export`: preserve raw Organization export rows separately from readable workbook projections and the existing narrower single-Person workbook.
- `artifact-retention`: delete only expired archived artifacts, remove files for deleted rows, preserve active/recent/foreign sentinels and report truthful counts and failures.
- `artifact-storage-responses`: document signing rejects malformed replies; admitted cleanup preserves already-missing objects while rejecting malformed or unrelated deletion acknowledgments and keeping known partial effects explicit.
- `artifact-switching`: a Person or Organization change and late responses cannot carry the previous record's draft, saved items or file access into the next record.

## How to get to it (user POV)

Choose Personnel, find a Soldier and select Details. The record header names the Person and holds Edit, `More Personnel record` (Export records, Archive) and `Add to record`; the tabs below it are Overview, Readiness, Log, Files, Data sheet and Archived. Overview provides Follow-up, Counseling PDF, Document and Leader note forms and recent-item previews. Use Show all, or Log (follow-ups and notes) and Files (counselings and documents), for their complete lists. The Log tab badge counts open follow-ups and the Archived tab shows its item count. Follow-ups supports Edit, Complete/Reopen and Archive; counselings, documents and notes provide Archive. Documents provides Open. Archived combines all four families and provides Restore and Delete for each item.

Follow-up, Note, Counseling and Document appear in `Add to record` only for a member who may manage and read sensitive records, because Log and Files require that read. Training completion follows Training record completions. Export records appears only with Personnel export. `Add to record` items only navigate: Follow-up and Note open Log, Counseling and Document open Files, and Training completion opens Readiness. None opens or focuses a form yet. Counseling cards show the filename but currently provide no Open or download action. Do not invent a native counseling-file journey. Its authenticated Storage access is a separate provider/security obligation.

Use `More Personnel record` → Export records in the record header for the single-Person workbook. An Organization owner/admin uses Settings → Exports for complete Organization JSON and Excel, and Settings → Archives for parent Personnel restore. Scheduled retention has no user-facing run button; its admitted job call and provider/file effects are separate from the visible Archived list.

## Provider faults and recovery

D05 requires recoverable file cleanup and preservation of committed uploads. The following cases are intended outcomes, not accepted baseline behavior. Use the owned provider controls documented in the skill, preserve every `fault state` receipt and restore each fault before retry or cleanup.

- Upload a real synthetic document or counseling PDF through the native form with its `document-attach-lost-ack` or `counseling-attach-lost-ack` fault armed. The provider commits the metadata row but the app receives 503. Read back the exact row and file hash. A lost reply must not cause compensation to delete a file referenced by a committed row. Record the visible saved or uncertain state, reload, and inspect whether retry can create a duplicate.
- Archive a real uploaded document or counseling and arm `document-file-remove` or `counseling-file-remove`. Confirm Delete natively. Preserve the exact metadata, recorded file path and bytes, actual error or completion response, and any durable cleanup work. Reload before retry. Read the durable receipt with `$V artifact-deletion orgA PERSON_ID document|counseling ARTIFACT_ID`. This privileged readback is separate from ordinary retry authorization. Cleanup must remain discoverable after metadata deletion; a missing row alone is not recovery. Restore the control and drive the implemented retry or admitted maintenance path. Verify the recorded path is absent and unrelated active, recent and foreign files remain unchanged.
- Repeat removal with the matching `-lost-ack` fault. Its receipt must show the real provider succeeded before the synthetic 503. Recovery must converge when the file is already absent, without touching another file or inventing a rollback.
- Use the [deletion request provider-failure case](deletion-requests.md#driving-it-with-verifyapp) for an approval whose status write is rejected. The losing approval must preserve the source row and its bytes. Actual competing terminal reviewers and restore-versus-delete require separate isolated SQL or service interleaving proof, not a browser response hold.

## Gotchas

- Archive, Open, Restore and Delete repeat per item. Use a fresh snapshot and the named row; preserve the selected ID alongside the action. Delete opens a destructive `Delete archived item` confirmation: Cancel and Escape send nothing and return focus to Delete. Confirm keeps the dialog open and busy (Cancel, Confirm disabled, Escape ignored) until the DELETE settles; a failure keeps it open with a destructive Alert and Confirm retries; success closes it and focus goes to the next row's Restore, else the previous row's, else the `Archived` heading. The seeded document is metadata only. Its deletion must succeed when Storage confirms the object is already absent.
- The recorded outcome comes from visible actions plus saved row/file readback and reload. A closed form, disappearing card, signed URL or success toast alone is insufficient.
- Counseling file access has no current native entry point. Label authenticated Storage/SQL proof honestly; do not add an Open product feature merely to make the recipe executable.
- The [retained file rules](../../../../docs/domain/retained-feature-rules.md#personnel-documents-and-counseling) and [sensitive authorization contract](../../../../docs/architecture/AUTHORIZATION_AND_PROVIDER_BOUNDARIES.md#feature-permission-direction) own expectations. Keep the accepted note author fallback and 100-row composite-cursor traversal with complete legacy arrays; a small native list does not re-prove tied-timestamp or large-collection coverage.
- File cleanup crosses Storage/database calls. Document and counseling row deletion records cleanup in the same database transaction. Counseling approval commits its row/status transaction before removing bytes. A retired key cannot be reused. Pending cleanup is retried by the archive-retention job; this does not make Storage transactional.
- Preserve meaningful lower-level checks: Personnel `personnelCounselingRecords.server.test.ts`, `personnelDocuments.server.test.ts`, `personnelFollowUps.server.test.ts`, `personnelArchivedArtifacts.server.test.ts`, `personnelArtifactContext.server.test.ts`, delivery `personnelArtifacts.test.ts` (real SDK serialization under controlled finite REST), Organization member-label/document-cap collaborator tests; Personnel `personnelArtifactRetention.server.test.ts`, `artifactWrites.server.test.ts`, `leaderNotes.server.test.ts`, `governanceDeletion.server.test.ts`, `personnelLifecycle.server.test.ts` and `personnelLifecycleCommands.server.test.ts`, `personnelExport.server.test.ts` and `organizationExport.server.test.ts`; artifact draft/workspace/component tests; counseling/documents/notes page tests and artifact JSON/download route tests. Keep tests with the owning operation when cutover moves it; source-mirrored spec-registration tests are not behavioral acceptance.
- Run isolated SQL through the [Definition of Done](../../../../docs/architecture/DEFINITION_OF_DONE.md#isolated-database-checks): `personnel_sensitive_artifact_reads.sql`, `personnel_counseling_file_scope.sql`, `personnel_artifact_rls_group_scope.sql`, `personnel_leader_note_traversal.sql`, `counseling_deletion_approval_atomic.sql`, `personnel_lifecycle_atomic.sql`, `personnel_lifecycle_concurrency.sql`, `personnel_lifecycle_cohort.sql` and `feature_direct_write_authority.sql`. These establish RLS, Storage paths, traversal and request/record boundaries separately from native UI and authenticated HTTP. Never aim them at a remote or existing local database.
- Restore every armed control, compare retained rows/files, run final doctor, clean only recorded helper-created rows/files and dispose the owned worker. Preserve failures, unrun retention/provider boundaries and exact artifacts when packaging durable evidence; preparation alone does not complete the owning issue.
