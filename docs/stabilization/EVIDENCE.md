## 11-05c D09 Calendar re-entry freshness

**One PR closes #1689 on merge.** Branch `fix/1689-stabilization` began at fetched main `3ede6827ee39494a41518ecba20ab5032f9b52a8`. No earlier D09 branch or PR existed. Robert decided the freshness model on 2026-10-14 and authorized publication and merge after green CI and resolved bot feedback, continuing only within #1689 through its closing merge.

**Model.** A snapshot of a date range is authoritative only within that range and only up to the changes its tab confirmed after the request left. Every core-store write the server confirms is recorded explicitly through one reducer (`src/lib/stores/core/confirmedChanges.ts`, `createStore.svelte.ts`); confirmed updates upsert. Each browser tab numbers its own confirmed changes and writes the latest number to its own cookie, `t2t-confirmed-<tab>`. Every request, including navigation, hover preload and refresh, therefore carries the number its tab had confirmed when the request left. The Calendar and Dashboard deliveries echo those cookies, and hydration replaces the range, then re-applies every later change. The client-started range reads (month navigation, Bulk Status, D05's recovery read) begin their read just before the fetch. No server read time, tombstone or schema change exists.

- **Retention.** A store keeps changes for ten minutes and while an open read needs them. A snapshot whose needed changes were discarded throws, and the layout shows its existing load error with Retry. A request with no token for this tab is treated as recent.
- **Full reads.** Special Days' overlap recovery read takes a fresh number first, so any snapshot whose request left earlier changes nothing afterwards. D05's contract is unchanged: a failed overlap refresh leaves the store as it was and reports `saved-unrefreshed`.
- **Scope.** Availability, Special Days and daily assignments use range targets. The daily-assignment audit reproduced the hidden-save defect in the store and natively (case f), so assignments use the same model. Dashboard reconciles the shared availability and assignment stores within its own date range instead of replacing them. The add-only Calendar merge path is removed.
- **Kept protections.** Organization lifetime gating, the hydrator's request identity and `loadVersion` checks, range request serials, optimistic rollback and D05's recovery reads.

**Model.** The keyed Organization shell (`src/routes/org/[orgId]/+layout.svelte`) owns one lifetime per user, Organization and session. `AppShell` teardown ends it in `src/lib/stores/core/lifetime.ts`. A core-store, assignment, import or component request that finishes in a lifetime the user has left never settles back to its caller, so no destroyed caller applies it or reports it. A store also treats a load for another Organization, or its first load in a new lifetime, as a new lifetime and drops abandoned optimistic entries. Server writes are unchanged. This replaced about 30 caller-specific stale checks that a failure-shaped `null`/`false` result would otherwise need.
