# Organization profile, policies and destruction

An Organization owner or admin maintains its name, web address and policies; only its owner can delete it after name confirmation and current identity verification.

## Sub-features

- `profile-name`: confirmation, cancellation, saved name, reload and current Organization labels.
- `custom-url`: valid slug, conflict and invalid input, canonical links, UUID access and reset to the default address.
- `organization-policies`: independent retention and loss-warning saves, retained drafts on failure, and the separate document-cap API contract.
- `settings-target-isolation`: Organization switches reset drafts and busy state; an old target’s pending response cannot mark the new target saved or announce success/failure there.
- `governance-denial`: ordinary members, foreign Organizations and stale governance cannot change saved settings or destroy an Organization.
- `destruction-safeguards`: owner-only admission, matching name, cancellation, real elapsed-session step-up and an explicit retry after verification.
- `destruction-effects`: Dashboard return, removed membership/current-target access and observed same-Organization cascades while foreign rows remain unchanged.
- `unit-route-disposition`: effective schema and real caller evidence classify the legacy endpoint separately from supported Group management.

## How to get to it (user POV)

Open `Settings` in the Organization navigation. `General` contains `Organization Profile`, `Edit` for the Organization name, and `Custom URL`. `Policies` contains `Archive Retention` and `Loss Warning Window`, each with its own `Save` button. Owners also see the `Danger` tab: select `Delete <Organization name>`, type that name in `Delete Organization`, and use `Delete Permanently`. An admin's direct Danger visit returns to General; an ordinary member cannot enter Organization Settings.

Ownership transfer is already described in [Manage Organization member access and ownership](organization-member-access.md). Reuse applicable D05 evidence or repeat that recipe when changing its shared Danger delivery, candidates or identity handoff. Keep sole-owner transfer, former-owner Admin status and stale-authority denial accounted for without maintaining a second transfer recipe.

## Driving it with verify:app

Preconditions: run the owned worker's `doctor` and `fixture`; retain candidate, origin, actor and exact A/B Organization and membership IDs. Use `$V actor orgOwner settings/general`, `$V actor orgAdmin settings/general`, and `$V actor orgMember personnel` in isolated contexts. `$V actor orgSettingsPeer settings/general` admits only B's owner; `$V actor orgSettingsSwitch settings/policies` admits the same admin in A/B with no feature lanes. Read `$V rows organizations orgA` and `$V rows organizations orgB` and the exact A/B membership and affected resource rows before changing anything. The setting readback includes name, slug, retention, loss-warning, document cap and retained Critical Tasks defaults. Record snapshots, visible action results, request status/envelope and readback after reload separately. Perform deletion last on this disposable worker, after other journeys that require A. Never target an existing development or remote Organization.

For direct JSON/form observations below, use the supported `settings-request PAGE orgA|orgB FAMILY JSON` helper in the normally signed-in native page. Supported families are `organization/settings`, `settings/general/updateName`, `settings/general/updateSlug`, `settings/general/clearSlug` and `settings/danger/deleteOrganization`. Submit JSON scalar fields for policies/cap, `{"name":"Synthetic name"}`, `{"urlSlug":"synthetic-slug"}`, `{}` for clear or `{"confirmName":"<saved name>"}` for deletion. Example: `$V settings-request "$PAGE" orgA organization/settings '{"personnelDocumentStorageCapMb":11}'`. It returns the transport status and full action envelope without applying a result to the UI or following redirects. Capture the actual direct request separately from native clicks; use only synthetic values, record before/after rows and restore successful edits. Do not use a denied actor’s missing page as evidence of a valid action denial.

1. **Name confirmation and persistence.** As `orgOwner`, open General → `Edit`, enter a unique name of at most 100 characters and choose `Save`. Cancel `Update organization name?`; the saved name and Organization ID remain unchanged. Reopen and confirm `Update Name`. Require successful feedback, the same saved Organization ID and normalized name after reload; compare General, the settings heading and Organization navigation. Repeat one ordinary save as `orgAdmin` to establish governance admission independently of owner authority. Cancel an edited draft and require the saved name to remain. A blank direct action must fail without changing the row. For a pre-request name failure, use `$V network arm-fail $PAGE settings/general/updateName` on A's current canonical General route; record error/retry behavior and unchanged saved name; otherwise keep that live failure path unrun and retain the existing provider-failure checks separately. Restore the original name through the UI before other recipes depend on its exact confirmation text.

2. **Custom address and retained route identity.** Enter a unique slug such as `verify-settings-<tag>` and confirm `Update custom URL?`. Follow General, Policies and a retained Personnel or Calendar link; reload and confirm the same target and data. A direct visit using A's UUID must still resolve A. Change to a second unique slug, observe the new canonical path, then check that the old slug no longer resolves A. Exercise a reserved slug such as `admin`, a malformed slug such as `alpha--bravo`, and a short slug; capture useful errors and unchanged saved row. For a true conflict, use a known slug already assigned to B through that Organization's admitted UI or a recorded owned setup fixture; submitting it for A must fail and preserve both Organizations. A repeated slug on A is permitted. Cancel `Reset custom URL?` and require unchanged persistence, then confirm `Reset URL`; require the UUID General path, null saved slug, canonical UUID links, and no access through either retired custom slug. A failed lookup is distinct from a duplicate: retain provider-failure proof separately when no live control exists.

Restore the original policy values through the UI. ## Gotchas

- General/Policies admit owner or admin roles. High feature capabilities or Group scope do not grant governance; Danger deletion remains owner-only and sensitive-action assurance supplies no additional role permission.
- Name changes retain the Organization ID; slug changes affect bookmarks but preserve UUID access. Use exact IDs for provider readback so a changed route segment cannot silently change the tested target.
- `network arm-fail` prevents one ordinary UI request at the browser boundary. It establishes client retry behavior and unchanged storage, not a failed provider write, concurrency or transactional rollback. Restore every armed control before another path.
- Deletion ends the fixture's normal membership access. Capture prerequisites and exact resource IDs first, drive it last, and use owned cleanup/restart; do not turn fixture deletion into deletion of existing local development data.
- Row cascades, durable audit and Storage bytes are separate outcomes. The current Organization deletion provider deletes its scoped Organization row; any missing effect stays visible for D17's implementation decision.
- Keep existing focused `orgSettingsAdministration`, URL-slug, Organization ownership-transfer/provider/workspace, settings shell/load/danger and settings API checks, plus applicable isolated SQL such as `org_ownership_rpc_contract.sql`. There is currently no General route-action test file. Tests, direct requests and catalog reads complement native UI observations; none substitutes for another.
