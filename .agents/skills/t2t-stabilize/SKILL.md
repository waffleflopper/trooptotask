# Continue stabilization to the next PR

Own the selected issue through the next complete, reviewable PR. Read the [stabilization workflow](../../../docs/agents/stabilization-workflow.md) and current [#1275](https://github.com/waffleflopper/trooptotask/issues/1275) for phase dependencies, safety, checkpoints and release rules. Use [t2t-engineer](../t2t-engineer/SKILL.md) for engineering and independent acceptance, [verify-trooptotask](../verify-trooptotask/SKILL.md) for app verification, and the repository's [finish-pr](../finish-pr/SKILL.md) for PR feedback and current-head checks. Reach these skills as part of the continuation; Robert does not need to invoke verification separately. Keep this skill as coordinator when using shared pstack methods under the [integration rules](../../../docs/agents/operating-rules.md#shared-skills-and-project-workflows). If local finish-pr is unavailable, report that limit and fulfill the same PR obligations below through available Git/`gh`/host tools under [operating rules](../../../docs/agents/operating-rules.md); do not substitute a global workflow or claim the skill ran.

“Continue issue X through its next verified PR; you may publish, I'll merge” includes missing feature recipes, fixtures or controls, authorized baseline repairs, implementation, review fixes and publication. It supplies the workflow's explicit request to fix the selected open PR. Carry that authorization through the invocation and stop for Robert's review and merge. A narrower request keeps its narrower scope; this skill adds no publication, communication, tracker, merge, deployment or database authority. Another issue or phase needs its own authorization.

## Reconcile before selecting work

Read the selected issue, parent, relevant comments, [TODO](../../../docs/stabilization/TODO.md), relevant [EVIDENCE](../../../docs/stabilization/EVIDENCE.md), retained contracts and program decisions. Compare local branches/worktrees and dirty or unpushed work with freshly fetched default content and actual open, closed-unmerged and merged PRs. Use paginated Git/`gh` reads with verified repository/head/base and issue links; titles alone are insufficient. Account for squash/rebase integration. Inspect review threads and exact-head CI for an open PR. Register each PR actually worked on with T3's `link_pull_request` when available and check thread links before handoff.

A closed issue, checked task, green CI badge or recorded PR number cannot establish completion. Classify remaining acceptance as delivered with applicable evidence, required for this PR, or remaining afterward, retaining failed/unavailable results and owners. Resolve competing branches or ambiguous identity before dependent edits; preserve ongoing work. Finish reconciliation with the current stage, intended PR scope, issue remainder and available authorization clear.

## Establish the affected baseline

Use the repository-owned `verify:app` environment, native browser controls and documented verify-trooptotask helpers for stabilization proof, regardless of the communication app or harness. Use an integrated browser only at Robert's explicit request, as required by [AGENTS.md](../../../AGENTS.md). Browser availability or failure does not change that default.

Read the authoritative [feature-map index](../verify-trooptotask/features/README.md) and relevant feature files before the affected cutover. Derive expected behavior from approved product rules and issue acceptance, then inspect current recipes and any existing lower-level checks for the behavior they actually cover. Extend or correct missing recipes, fixture roles and small reusable controls as necessary. This is worker work within the selected issue, not a separate assignment for Robert or a requirement to encode every behavior as a browser test.

Use verify-trooptotask to drive the affected features and dependencies on the unchanged application. Combine compatible setup and scenarios while covering relevant entry points, denied access, failure, persistence and scope changes. Source inspection is not live verification; direct authenticated API or SQL checks are separate security/provider proof, not UI interaction. Keep baseline and final observations distinct, with the tested code version, environment, role, actions, expected/observed results and durable sanitized artifacts. Reuse applicable completed evidence only when it still covers the unchanged behavior and candidate; explain its applicability.

Routine issue work covers affected features and dependencies. A broader source/live upkeep pass belongs to an explicit [maintain-verification-skill](../maintain-verification-skill/SKILL.md) invocation. Maintain one feature map; do not create issue claim JSON, a second checklist registry or a replacement evidence gate.

## Select the next stage

Stages guide decisions within the existing checkpoint, not another persisted state machine. Reassess after new evidence or a merge.

| Observed state                                           | Next action and completion criterion                                                                                                                                                                                                                                          |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| An affected feature, fixture role or control is missing  | Extend the relevant recipe and reusable setup/control, exercise it on the unchanged app, then continue the scoped change. A cohesive verification-only PR is possible when that is the selected outcome.                                                                      |
| Required live evidence is missing, stale or inconclusive | Run or repair the owned controls and collect applicable baseline/final observations. Unavailable tools remain blockers only to the proof they own; continue independent work.                                                                                                 |
| A product defect fails the baseline                      | Reproduce against approved expectations. Repair it when the selected issue/request owns it, then reverify the affected baseline. Otherwise name its owner and precise dependency and seek only missing authority. Never redefine the expected result to make the defect pass. |
| The contract requires a consequential product choice     | State the conflict or unspecified behavior and ask the smallest decision needed while continuing independent work. Missing instructions, fixture capability or a known expected result are engineering work.                                                                  |
| The affected baseline passes and implementation remains  | Have t2t-engineer finish the scoped operation, affected consumers and removals; then repeat affected live verification and lower-level checks, updating recipes as behavior changes.                                                                                          |
| An open PR needs fixes or current evidence               | Resume that PR with finish-pr within its declared outcome; inspect feedback, fix actionable defects and reverify changed paths. Reuse completed work instead of creating a competing PR.                                                                                      |
| An intermediate PR merged                                | Verify integration and acceptance, subtract only delivered requirements, reconcile premature closure below and continue the same authorized issue from updated default in a safe worktree.                                                                                    |
| A PR closed without merging, or linkage is ambiguous     | Preserve its work and investigate. It earns no integration credit; establish safe continuation within authorization.                                                                                                                                                          |
| Every issue requirement is accepted and integrated       | Report completion, reconcile authorized tracker state and stop. Do not invent another PR or advance to another issue/phase.                                                                                                                                                   |

## Bound the PR without shrinking the issue

Choose a cohesive result worth reviewing: usable verification coverage, a reproduced baseline repair, or a complete owned seam and affected consumers. Declare acceptance and exclusions before edits. Keep each whole-issue requirement accounted for as delivered, this PR or remaining in the existing task artifacts; use the PR body for review scope. Keep progress in TODO/EVIDENCE and link the authoritative feature recipes rather than duplicating them.

**PR complete** means its declared outcome and affected consumers are finished, required checks and behavioral evidence pass for its candidate, and consequential review findings are resolved. **Issue complete** additionally requires every acceptance item, consumer/removal obligation and required evidence to pass on the integrated result, with all necessary PRs merged. A final PR awaiting merge is ready to complete the issue, not an already completed issue.

For an intermediate PR, select affected feature recipes and lower-level checks with a scope rationale in the existing evidence or PR. Independent acceptance assesses direct and reverse consumers, the selection's sufficiency and all remaining whole-issue obligations. Keep failures visible; narrowing scope after a failed observation cannot turn it into success. A verification-only PR may truthfully expose a product defect when that was its declared outcome; keep the issue open and dependent cutover blocked. A repair must prove repaired behavior, and a refactor cannot exclude a failure in its affected contract.

Use `Refs #<issue>` for intermediate PRs. Only a final PR satisfying pre-merge acceptance, with authorized closure on merge, uses `Closes #<issue>`; never close the phase parent from a PR. Inspect the whole PR title/body and included commit messages for unintended closing references before publication.

If an intermediate merge prematurely closed the issue, compare remaining requirements/failures with the merged diff and fetched default. With applicable [tracker authority](../../../docs/agents/issue-tracker.md), reopen the unfinished child and correct misleading completion/dependency state, preserve human edits and read back the result. Publication alone grants no tracker authority. Without authority/access, prepare the exact correction and report that blocker while continuing independent authorized work. Premature closure never unlocks dependents. Reuse an existing correction instead of repeatedly commenting. Close a genuinely finished open issue only with verified integrated acceptance and applicable authority. An explicit deferral of tracker updates takes precedence over these defaults.

## Verify, review and finish

Arrange acceptance independent of implementation. Give the reviewer the declared PR scope, whole-issue requirements/remainder, complete diff, affected recipes and actual evidence. Ask whether the required behaviors and consumers are covered and whether observations establish them. An independent runner may drive its own isolated session; reviewing artifacts is not independent live execution. Missing independent acceptance remains visible.

Use CodeRabbit for the intended diff. Inspect installed CLI help and existing results first; specify the actual base and committed/uncommitted scope. Record reviewed base/head or patch, scope and consequential dispositions in the existing work record. Reuse review of unchanged material, fix actionable findings and reverify affected behavior. Request another review only for changed material or consequential unresolved uncertainty. Optional suggestions are not gates. Pending, rate-limited or unavailable review is not a clean result; use bounded retries and report the missing review.

Apply the [Definition of Done](../../../docs/architecture/DEFINITION_OF_DONE.md#required-commands) and use local [finish-pr](../finish-pr/SKILL.md) through the authorized stopping point. It owns paginated feedback handling, authorized replies/resolutions and current-head CI. Reuse applicable exact-candidate [Depot evidence](../../../docs/ci.md); distinguish unsupported check APIs from actual CI failure and inspect available read-only host/Depot results. Publication may occur with checks pending when authorized, but label the PR unverified until required checks and requested reviews finish. CodeRabbit success does not replace live or independent acceptance evidence.

Fix in-scope review failures without another request. Changes after review/proof need affected reverification; new heads need current-head CI. Stop at a complete PR or a concrete blocker within available authority/capabilities. Never merge under this invocation.

## Parallel work and handoff

Use the workflow's [bounded parallel rules](../../../docs/agents/stabilization-workflow.md#bounded-parallel-work) and t2t-engineer's worker briefs. Assign exclusive files/worktrees/services and check actual capacity. Different feature-map files may have different worker owners; coordinate shared controls, fixtures, contracts, manifests, TODO/EVIDENCE and integration deliberately. One coordinator drives each owned browser. Freeze executable inputs during proof, integrate one PR at a time and reverify affected behavior after base changes. Independent read-only review does not activate parallel application workers. No new pilot or scheduler is required.

Every handoff names the issue/checkpoint, PR URL/base/head, what the PR completes, whether the issue is finished, remaining requirements/failures and owners, actual checks/reviews, release obligations and Robert's next action. For a verified intermediate PR: “Review and merge this PR; then repeat the continuation request.” For a blocker, name the precise decision, authority or unavailable capability. Inspect publication/deployment configuration and disclose unknown external settings under the workflow's release rules.

When changing this skill, exercise [the decision fixtures](references/decision-fixtures.md) with an independent reader and no live mutations. Record outcomes in the tooling PR, not stabilization progress.
