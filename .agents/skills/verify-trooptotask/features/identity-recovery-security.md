# Identity recovery, MFA and account security

A member completes a second-factor challenge, recovers a forgotten password, activates an invited account, changes their password and authenticator from Account Security, and a visitor requests access. A suspended account sees only the suspension screen.

## Sub-features

- `mfa-challenge`: an account with a verified authenticator signs in, lands on Two-Factor Authentication, is rejected for a wrong code and admitted for the current code. Its `sign out` link leaves the pending session.
- `password-recovery`: Forgot Password accepts any well-formed address with the same confirmation and rejects a malformed one. A recovery link opens the passive `/auth/confirm` review page; continuing sets a new password on Reset Password, and the new password signs in.
- `invite-activation`: an invite link continues to Accept Invite, which sets the first password. Renew Invite validates and accepts a setup-link request.
- `account-setup`: Account Setup without a valid setup link shows its unavailable state and recovery links.
- `request-access`: Sign Up redirects to Request Access. The form validates required fields and stores one pending Access Request.
- `account-security`: a signed-in member changes their password and enrolls then removes a TOTP authenticator.
- `suspended`: a suspended account reaches only Account Suspended, with Sign out.
- `logout-page`: the no-session `/auth/logout` page offers Sign in.
- `link-errors`: an incomplete or used confirmation link shows Link unavailable; Reset Password and Accept Invite without their flow show their unavailable states.

## How to get to it (user POV)

From Sign In, follow Forgot password, Request access or Request a fresh setup link. Recovery and invite emails open `/auth/confirm`, which waits for an explicit Continue button. A signed-in member opens Account menu → Account, then Security for password and Two-Factor Authentication. An account with a verified authenticator sees Two-Factor Authentication after the password step.

## Driving it with verify:app

Preconditions: doctor passes on the owned worker; record its candidate, origin and Chromium version. `$V fixture` lists the dedicated Organization A members `identityMfa` (verified TOTP factor from seeding), `identityRecovery`, `identitySecurity` and `identitySuspended` (a `user_suspensions` row). These accounts exist only for this recipe because their credentials, factors or suspension change; never reuse them for another feature's journey. Use `$V actor ROLE dashboard` for their sign-in and a fresh `tool new_page` context for public pages.

The private-credential controls fill visible fields without printing values:

- `$V mfa-code PAGE ROLE LABEL [OCCURRENCE]` reads the role's newest TOTP factor inside the owned provider and fills only the current six-digit code into the named textbox. The factor secret never leaves the provider control.
- `$V password PAGE ROLE current|next LABEL [OCCURRENCE]` fills the role's current password, or one generated replacement kept in private worker state. `$V password-commit ROLE` adopts the replacement after the visible save succeeds, so later `actor` sign-ins use it. The daemon's `login` command keeps the launch credentials, so use `actor` for these roles.
- `$V auth-link PAGE recovery ROLE` (or `auth-link PAGE invite` for a new synthetic address) asks the owned provider's admin API for the link the app's email would carry, navigates the named owned page to the app's `/auth/confirm` URL and prints a snapshot with the token redacted. Do not `take_snapshot` or `list_pages` on that page before Continue; native screenshots carry no URL.
- `$V access-request EMAIL` reads stored Access Requests for one lowercase `@example.test` address.

1. **MFA challenge.** Run `$V actor identityMfa dashboard`; the helper stops on `/auth/mfa-verify` with `Verify your code`. Capture the page. Type `000000` in Verification Code with native `fill` and press Verify: `Invalid verification code` (or the provider's rejection) shows and the page stays. Run `$V mfa-code PAGE identityMfa "Verification Code"`, press Verify and require `/dashboard` with Organization A. In a second `actor identityMfa dashboard` context, choose the `sign out` link instead: require the public page, and navigating to `/dashboard` must return to sign-in rather than the challenge.
2. **Forgot password request.** In a public context open Sign In → Forgot password. Submit `not-an-email` and require `Enter a valid email address` with the value retained. Submit `identityRecovery`'s email (from `$V fixture`) and then an unknown `nobody-RUN@example.test`: each shows `Check your email` with `If an account exists for` and the entered address. The worker has no Resend configuration, so no email leaves the worker and the visible confirmation is the only observation; it must not reveal whether the account exists.
3. **Recovery link and new password.** In a fresh public context run `$V auth-link PAGE recovery identityRecovery`. Its redacted snapshot shows `Confirm your password reset` and `Continue to Password Reset`; capture a native screenshot. Click Continue with the printed UID. Require `/auth/reset-password` with New Password and Confirm New Password. Submit mismatched values first (one field via `password ... next`, the other by native `fill`) and capture the mismatch error. Then fill both with `$V password PAGE identityRecovery next "New Password"` and `... "Confirm New Password"`, submit and require `Password updated`. Run `$V password-commit identityRecovery`, sign out, and prove persistence with `$V actor identityRecovery dashboard`. Re-running the same link is impossible because the token was consumed; a second `auth-link` produces a new link. The control proves link handling, not email delivery.
4. **Invite activation and renewal.** In a fresh public context run `$V auth-link PAGE invite`; continue with `Continue to Invite Setup` and require Accept Invite's Password and Confirm Password. Native `fill` may use a run-local synthetic password here because the new address has no fixture credentials; keep it out of notes. Submit and require `Account activated`, then the dashboard without any Organization membership. Separately open Request a fresh setup link (`/auth/renew-invite`): submit an empty and malformed email for validation, then a synthetic address, and capture `Check your email`.
5. **Account setup.** Open `/auth/setup-account` without a link and capture `Setup link unavailable` with its recovery links. Completing setup requires a token from an approved Access Request's setup email; the worker has no capture for that link, so a valid setup completion is unreachable here. [Platform administration](platform-administration.md) owns approval and setup-link issuance.
6. **Request access.** Open `/auth/sign-up` and require a redirect to `/auth/request-access`. Submit empty required fields and capture the field errors. Fill First Name, Last Name, a unique `access-RUN@example.test`, choose Where did you hear about it?, fill Unit or Reason and submit. Require `We've got your request`. `$V access-request access-RUN@example.test` must return one `pending` row with the submitted name and reason. Submitting the same address again shows the app's retained duplicate behavior; record it and the row count.
7. **Account security password.** `$V actor identitySecurity dashboard`, then Account menu → Account → Security. Fill Current password (occurrence 2; the email section owns the first) with `$V password PAGE identitySecurity current "Current password" 2`, a wrong-length New password by native `fill`, and capture the requirement list. Then fill New password and Confirm new password with `next`, submit and require the success message. `password-commit`, sign out and `actor identitySecurity dashboard` again.
8. **Account security MFA.** On Security choose Enable MFA. Capture the QR code panel (the code image is the only secret carrier; do not decode or copy it). Run `$V mfa-code PAGE identitySecurity "Verification code"` (the unverified factor) and Verify and Enable; require Enabled. Sign out and sign in with `actor identitySecurity dashboard`: the challenge appears, and `mfa-code ... "Verification Code"` admits the session. Back on Security, choose Disable MFA, fill Authenticator code with `mfa-code`, Confirm and Disable, and require Disabled. Cancel and Keep MFA Enabled paths must leave the status unchanged.
9. **Suspended.** `$V actor identitySuspended dashboard` lands on `/suspended` with `Account Suspended`. Navigate to `/dashboard` and `/org/ORG_A/personnel`: both return to `/suspended`. Use Sign out and require the public page.
10. **Logout and link errors.** Signed out, open `/auth/logout` and capture its Sign in path. Open `/auth/confirm` with no query and `/auth/confirm?type=recovery&next=/auth/reset-password&token_hash=used` and capture `Link unavailable` for the first and the invalid-link sign-in error after Continue for the second. Signed out, open `/auth/reset-password` and `/auth/accept-invite` and capture `Reset link unavailable` and `Invite unavailable`.
11. **Appearance and keyboard.** For the MFA challenge, Forgot Password, Reset Password, Accept Invite, Request Access, Account Setup, Suspended and Account Security screens, capture 1280x800 light and 390x844 dark, plus 1280x800 dark and 390x844 light for one Auth Shell page. Use `resize_page` and the visible Toggle theme where present; Auth Shell pages share the public toggle. Tab through each form: every field is reachable in order with a visible focus ring, Enter submits, and an error is announced next to its field.

Record provider-visible effects (Access Request rows, factor status through the Security page, suspension) separately from visible UI. Owned worker cleanup discards the changed identity accounts.

## Gotchas

- Supabase TOTP is enabled only in the disposable verify provider's generated config; the repository `supabase/config.toml` still leaves it off for local development. Every other auth, signup, password and rate-limit setting stays as configured.
- The sign-in, recovery and MFA endpoints share provider rate limits. Pace attempts and record a 429 rather than retrying in a loop.
- `/auth/confirm` intentionally waits for an explicit button; a link prefetch does not consume the token. A used or expired token redirects to sign-in with an invalid-link error.
- A recovery or invite session is restricted to its password page until the password is set. Leaving through `Need to exit?` ends it.
- `identitySuspended` keeps its suspension for the worker's lifetime. Platform administration's suspension journey uses its own seeded accounts and restores them through the UI.
