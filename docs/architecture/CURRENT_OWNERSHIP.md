**Cross-owner SQL and transaction authority.** Organization's membership/Group scope facts feed Access Platform helpers and feature-owned RLS; Personnel scope checks are used by Calendar, Training, Critical Tasks, Onboarding and Rating Scheme. The Sign-in Roster and sensitive-file helpers read Personnel scope while keeping their own record/path rules. Onboarding's `onboarding_template_training_type_matches` reads Training definitions. [Organization provisioning](../../src/lib/server/adapters/supabaseOrgProvisioning.ts) calls `create_org_with_owner` for the Organization and owner membership, then separately seeds Personnel Group/rank and Calendar defaults; the RPC's transaction does **not** make all of those later writes atomic. Platform support projections read Organization memberships, Personnel counts and Audit records through privileged adapters. `reject_access_request_and_block_linked_invitations` is the Platform Administration transaction that updates Identity request and Organization invitation/link state together. Invitation acceptance locks/updates invitation and membership and touches Identity setup facts. The retained rank-delete RPC checks Personnel, Training and Sign-in Roster references in one database transaction; Calendar's assignment-type retention RPC must protect persisted assignment references. Rate-limit increments and auth-email sync rely on their effective SQL function/trigger transactions, not a TypeScript multi-call transaction promise. Data Export reads source tables, not ownership of their policies. Current broad `src/lib/server/core/ports.ts` and generic `supabaseDataStore` still let callers name foreign tables; D01 records that current placement, while D03/Phase 08 own actual cutovers.

**Intentional provider bindings.** Supabase Auth `auth.users`/`auth.uid()`, request session/MFA and admin operations belong to Identity or Platform Administration at their current admission/support edges; Organization invitation/provisioning SQL and membership FKs retain the same provider subject values. Access Platform owns current trusted membership/policy evaluation, not identity creation. Provider Infrastructure owns connection/service-role and PostgREST mechanics; feature-owned adapters map rows and errors without transferring policy ownership. Provider Storage Access owns shared `storage.objects` path/policy helpers; Personnel counseling/documents and Sign-in Rosters own their private-file business scopes. Supabase Realtime is configured, but this public catalog's publication record alone does not establish a current feature subscriber or hosted publication membership. Preserve effective RLS, function security/EXECUTE grants, Storage policies, auth triggers and current identifiers; the [trusted identity and access contract](AUTHORIZATION_AND_PROVIDER_BOUNDARIES.md#trusted-identity-and-access-contract-07-01c) states their current guarantees and D03/Phase 08 cutover direction. These bindings are current infrastructure, not abandoned compatibility paths or a future-provider migration plan.

## Observed dependency pressure

- Dashboard currently imports Calendar and Training mutable stores in `src/features/dashboard/dashboardWorkspaceHydration.svelte.ts`; its screen read model also reads Calendar stores and Rating Scheme calculations. Dashboard owns the composition, while those source owners retain data and policy.
- Onboarding currently imports Training store/types and scoped roster data in `src/features/onboarding/onboardingWorkspaceHydration.svelte.ts`. Training and Personnel remain the source owners.
- Server feature entry points still reach central `src/lib/server/core/ports.ts`, `src/lib/server/adapters/httpAdapter.ts` and central entities, for example `src/features/rating-scheme/server/ratingSchemeWorkspaceBootstrap.ts`. This is current placement, not evidence that the target public/server boundary exists.
- Routes deep-import feature contexts, stores, components and server bootstraps, for example `src/routes/org/[orgId]/calendar/+page.svelte` and `+layout.server.ts`. The D01 contract and D02 checker must distinguish legitimate delivery imports from private cross-owner imports; this inventory does not enforce either yet.
