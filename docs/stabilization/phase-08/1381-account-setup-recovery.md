# Account setup recovery — issue #1381

## Candidate and behavior

This follow-up branch starts at `main` merge commit `b8fedc276ee512043f99856b883174941714dd75` for [PR #1380](https://github.com/waffleflopper/trooptotask/pull/1380). The reviewed source is the diff from that commit through the commit containing this record. #1380 is merged and #1350 is closed. This separately requested fix does not activate D03.

A claimed setup link now has a database attempt row. The Auth-user trigger consumes a transaction-local marker during admin create or password update and records the committed Auth write in the same transaction. A second same-email setup reconciles that specific attempt: it completes a committed write without setting a new password, or fences an unwritten attempt before a new password write. An approved or link-bearing Access Request cannot change email and move a held attempt outside that scope. Finalization checks the approved request, live link, Auth-owned email identity, and any existing request user ID, then writes the profile, Access Request and link together. Legacy or unresolved inconsistent claims require the audited staff release path. A duplicate Auth user missing from the identity index is fenced and instead needs staff identity repair; releasing that failed link is not useful. Organization membership remains a separate invitation-acceptance step.

The setup page exchanges a raw link for a signed, tokenless, ten-minute session. A claimed session and a fresh same-email link offer **Check setup status**. A committed result survives reload without another password submission; an unwritten result gives neutral guidance to use the fresh link. The action is rate limited and sends no service-role credential, raw token or account-existence detail to the browser. The support runbook and ADR/provider-boundary contracts describe the new path and its limits.
