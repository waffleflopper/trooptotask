## 12-03 D04 Dashboard initial and deferred load

### PR 1 streamed-response session refresh

**Repaired and proven live; the speed repair is not in this PR.** Refs [#1708](https://github.com/waffleflopper/trooptotask/issues/1708), found defect "streamed responses crash the server through `cookies.set`". A streamed load kept using the request's Supabase client after SvelteKit had generated the response. When the access token reached auth-js's 90 s refresh margin, the refresh called `cookies.set`, which throws then, and the unhandled rejection exited the Node process.

- **Prevention.** `readIdentitySession` (the Identity transport edge) refreshes the verified session before the response when it expires within 390 s: auth-js's 90 s margin plus a 300 s stream allowance. The rotated cookies ride the response headers, and a stream shorter than the allowance never refreshes. A failed refresh follows the existing stale-session handling (`STALE_SUPABASE_AUTH_ERROR_CODES`, cookies cleared, anonymous). Any other refresh error keeps the still-valid session. A fresh session adds no provider call.
- **Guard.** `createAuthCookieWriter` (`authCookies.server.ts`) writes provider cookies until `handle` marks the response generated, then drops them and logs one `[auth-session] { event: 'cookies_dropped_after_response', count }` warning with no names or values. The hook wires it and marks the response in a `finally` around `resolve`. A stream that outlives the allowance survives.
- **Allowance.** The repository sets no function `maxDuration` (`svelte.config.js` uses the default `adapter-vercel()`, `vercel.json` has no `functions`). 300 s is the default function duration Vercel documents (not verifiable from this repository), so it is the longest invocation the code assumes. The hosted limit and the hosted JWT lifetime are unknown external settings; local `supabase/config.toml` uses 3600 s. A hosted lifetime at or under 390 s would refresh on every request.
- **Limit.** A stream past the allowance still drops its one rotation, and the browser's refresh token is then consumed under `enable_refresh_token_rotation = true` with a 10 s reuse interval. The browser's next request after that interval presents a revoked token, and GoTrue can then revoke the session family and sign the user out (inferred from the configuration, not reproduced). Prevention makes this require a stream longer than the allowance; it is not removed.

**Tests** (`src/hooks.sessionRefresh.test.ts`, the real `@supabase/ssr` and auth-js client against a stubbed provider that rotates refresh tokens, plus `authCookies.server.test.ts`): a fresh session makes no refresh call and sets no cookie; a session 290 s from expiry refreshes once before `resolve`, sets `sb-refresh-auth-token`, and the next request authenticates on `refresh-1` with no second refresh; a refresh made after `resolve` through PostgREST completes, sets no cookie, logs the exact warning once and leaves no `unhandledRejection`. Without the repair the second and third fail (the third with the `cookies.set` throw from `applyServerStorage`).

**Live proof.** `verify:app` worker 2, Chromium 154.0.8037.97, Node 24.22.0, `dashboardView` Home from Calendar with `server-source arm ict_tasks hold 1 100000`, which delays the Critical Tasks summary's catalog read so its next read dispatches near the end of a 150 s token. The harness has no token lifetime control, so the worker's provider ran with `jwt_expiry = 150` through a temporary, uncommitted edit of `scripts/verification/environment.py` (reverted; no application change). Before, main `21058127b` (digest `1fe625e4…5b20`): the process logged `Cannot use cookies.set(...) after the response has been generated` through `applyServerStorage` and exited (`before-fix-app.log`). After, this branch (digest `26cca759…2a56`): the held summary completed (`[dashboard-load]` summary `durationMs: 98986`, `status: 'ok'`), the log shows one `cookies_dropped_after_response` warning with `count: 1`, `doctor` passed and the Dashboard rendered with no load-error alert (`after-fix-dashboard.png`). Artifacts in `.verification/evidence/d04-1708-stream-cookie-refresh/`: `before-fix-app.log`, `after-fix-app.log`, `after-fix-server-source-state.json`, `after-fix-dashboard.png`, launch receipts. In PostgreSQL's default `auto` mode a connection uses custom plans for a statement's first five executions and may then move it to a generic plan, but only when the generic plan's estimated cost is not much higher than the custom plans' average. `perf prepare` pins one regime: it sets `plan_cache_mode = force_custom_plan` on the `authenticator` role, turns on `pg_stat_statements.track_planning`, restarts PostgREST and reads the setting back through the request path. Every run records that readback before and after, and an unpinned run does not start. All 113 r6 runs were pinned before and after, and their windows hold 18,588 plannable app executions and 18,588 plans (`analysis/regime.md`); r4's 125 runs held 31,216 of each. Production's `auto` mode can move a long-lived connection to a generic plan, which D01 does not measure.

**Gate and host.** Each sample starts on a clear host and is watched every 2 s. It is rejected and measured again if the 1-minute load passes 4 at any reading, or if another checkout's build, test or verification processes use 25% of one core in any tick. More than five rejections stop the run. r6 rejected 11 samples while another checkout ran its checks, and measured each again (`analysis/rejections.md`). During kept samples the highest load was 3.74, and other checkouts' tools reached at most 8% of one core. A 5 s sampler logged load and other checkouts' processes for the whole run (`host/sampler.log`).

**Method.** Each seed is followed by `perf prepare`: it waits 11 s for the seed's insert counts to reach the statistics, runs `VACUUM (ANALYZE)` on exactly the seeded tables, then pins the plan regime. It took 12,008 to 12,152 ms on every r6 seed and 11,983 to 12,052 ms on every r7 seed. The warm order is the [recipe's](../../.agents/skills/verify-trooptotask/features/performance.md#protocol): seed and prepare, sign in, then 1 warm-up and 5 samples per journey. Cold runs use 3 samples, each a fresh context, for Calendar initial, Personnel list and Dashboard only, because of the auth rate limit. One 120 s cap bounds every wait. Each sample's statement window closes after its document ends. The owned preview streams app responses uncompressed, as production does. The workloads seed the redesign's lanes, short status labels and 105 special days.
