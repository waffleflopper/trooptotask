# Request and review archival or deletion

Ordinary members request approval when their source permission permits an operation but lacks direct archival/deletion authority. Organization reviewers approve or deny the request; requesters can cancel their own pending requests. This recipe owns D18 #1366's cross-feature workflow, alongside each source's existing recipe.

## Sub-features

- Personnel single and bulk archival, Training completion deletion and Rating Scheme deletion through their visible source controls.
- Retained authenticated Training type and counseling-record request interfaces; these have no current requester UI.
- Settings approval list, approval, denial with reason, requester identification, reload persistence and failure recovery.
- Own list/cancel, pending duplicate 409, reviewer admission, source policy admission, Group and foreign Organization protection.
- Approved Personnel archival, Training type/record and Rating removal; counseling row/status atomicity and separate file removal.
- Partial bulk outcomes and effect-before-status retry; file-bearing failures and concurrency remain separately identified provider/SQL proof.

## How to get to it (user POV)

Choose an Organization and open **Personnel**, **Training** or **Evals**. Use the source's Archive/Delete control as an ordinary operator. A reviewer opens **Settings → Approvals**, checks the description and requester, then **Approve** or **Deny**. Denial allows a reason. Reload and revisit the source to confirm the effect. Cancellation and retained Training type/counseling submission currently use the supported HTTP interface; do not describe them as visible UI.

## Gotchas

- Configure does not imply Organization governance review. Ordinary configure members still require approval where source direct-deletion policy says so; Training type configuration currently deletes directly.
- Current counseling UI archives/restores and permanently deletes archived artifacts; retained counseling requests are a different supported HTTP entry.
- Submission's identity admission does not establish source authorization; the source operation and approved effect have separate policy checks.
- Provider readbacks use privileged disposable access and establish persistence, not ordinary-user authorization. Native review and authenticated HTTP remain distinct.
- A verification-only PR can expose baseline defects without completing D18. Refactoring a failing contract waits for its owned repair and matching proof.
