## Contracts and consumer trace

Identity's `accountPreferences.server.ts` receives the ordinary request-user Supabase client and an already-admitted account/Organization scope. Its named reads preserve confirmed-absence defaults, legacy normalization and strict unavailable/unbound response errors. PATCH admits self policy, validates the existing patch schema and preserves unrelated Calendar/Training fields. Existing-row UPDATE compares the admitted user, Organization and exact raw JSON snapshot in the database; confirmed-absence insertion ignores a competing unique-pair insert. A genuine zero-row response triggers a fresh read/merge of only the caller’s patch, for at most three total attempts. Exhaustion returns HTTP 409. Every successful write must acknowledge exactly one admitted row and every intended known field before emitting `user_preferences.updated` or returning normalized choices. Provider errors and malformed acknowledgments are rejected rather than retried. A failed merge read cannot become a successful default snapshot. Upsert preserves existing row identity/history through the existing unique account/Organization key; schema and RLS are unchanged.

Getting Started reads return the current account's dismissal. POST acknowledges the saved timestamp, allowing equivalent provider timestamp formatting. DELETE preserves confirmed-absence no-op and resets an existing self row, with acknowledged null dismissal and retained identity/history. Provider errors and zero/mismatched responses cannot return success. Existing HTTP bodies, support counts, starter-pack support and self/member policy remain. No visible checklist exists and no new one is added.

The public `identity/index.server.ts` seam is consumed by `api/user-preferences/+server.ts`, `api/getting-started/+server.ts` and `supabaseOrgShell.ts`. HTTP delivery derives actor and canonical Organization, binds the ordinary client through `httpAdapter`, and converts owned status errors to SvelteKit errors. Getting Started delivery retains its existing source-owned setup counts, timing and starter-pack composition. AppShell retains parallel first-paint reads and its explicit display-default fallback outside the strict Identity operation. Existing Identity raw export readers and Data Export consumers remain unchanged; their raw-field contract and ordinary RLS are retained. No owner receives a universal route context or imports HTTP delivery.

The old preference PATCH performed two reads plus an insert/update. The final seam normally performs one read plus an acknowledged conditional write; collisions can require at most three such rounds. The database snapshot predicate protects disjoint concurrent fields across server instances, and duplicate-ignore insertion protects concurrent initial creation. Same-field changes resolve by the last successful database write. This is bounded optimistic concurrency using the existing JSONB column, without a process-local lock or a schema change.
