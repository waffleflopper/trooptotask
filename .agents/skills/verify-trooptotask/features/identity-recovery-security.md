# Identity recovery, MFA and account security

A member completes a second-factor challenge, recovers a forgotten password, activates an invited account, changes their password and authenticator from Account Security, and a visitor requests access. A suspended account sees only the suspension screen.

## Sub-features

- `mfa-challenge`: an account with a verified authenticator signs in, lands on Two-Factor Authentication, is rejected for a wrong code and admitted for the current code. Its `sign out` link leaves the pending session. Codes are limited per account.
- `password-recovery`: Forgot Password accepts any well-formed address with the same confirmation; the browser blocks a malformed one. A recovery link opens the passive `/auth/confirm` review page; continuing sets a new password on Reset Password, and the new password signs in.
- `invite-activation`: an invite link continues to Accept Invite, which sets the first password. Renew Invite validates and accepts a setup-link request.
- `account-setup`: Account Setup without a valid setup link shows its unavailable state and recovery links. A valid setup link opens Choose your password, and completion activates the User Account and signs in. A used link shows Account setup complete. Expired, replaced, failed and unapproved links show their unavailable messages. A link whose access was withdrawn (a revoked or blocked invitation, or a platform rescind) shows the withdrawn message, and a claimed link offers Check setup status.
- `request-access`: Sign Up redirects to Request Access. Submit stays disabled until the required fields are set, and a submission stores one pending Access Request.
- `account-security`: a signed-in member requests an email change and sees it pending, is rejected for an incorrect current password with the draft kept, changes their password, and enrolls then removes a TOTP authenticator. Its inline authenticator challenge for a session lacking the second factor has no normal-use route (step 8).
- `suspended`: a suspended account reaches only Account Suspended, with Sign out.
- `logout-page`: a GET of `/auth/logout` returns to `/`. Its page renders only after a sign-out POST. Signing out in a second tab that has no remaining session shows `Signed out on this browser.` with a Sign in link (step 10). The failed sign-out state (`Try signing out again.`, 503) has no normal-use route.
- `web-boundary`: the CSP allows no provider origin and blocks no app request; page data carries no session tokens; encoded paths share their request limits (step 12).
- `link-errors`: an incomplete or used confirmation link shows Link unavailable; Reset Password and Accept Invite without their flow show their unavailable states.

## How to get to it (user POV)

From Sign In, follow Forgot password, Request access or Request a fresh setup link. Recovery and invite emails open `/auth/confirm`, which waits for an explicit Continue button. A signed-in member opens Account menu → Account, then Security for password and Two-Factor Authentication. An account with a verified authenticator sees Two-Factor Authentication after the password step.

## Driving it with verify:app

Preconditions: doctor passes on the owned worker; record its candidate, origin and Chromium version. `$V fixture` lists the dedicated Organization A members, with their synthetic addresses under `identityEmails`: `identityMfa` (verified TOTP factor from seeding), `identityRecovery`, `identitySecurity` and `identitySuspended` (a `user_suspensions` row). These accounts exist only for this recipe because their credentials, factors or suspension change; never reuse them for another feature's journey. Use `$V actor ROLE dashboard` for their sign-in and a fresh `tool new_page` context for public pages.

The private-credential controls fill visible fields without printing values:

- `$V mfa-code PAGE ROLE LABEL [OCCURRENCE]` reads the role's newest TOTP factor inside the owned provider and fills only the current six-digit code into the named textbox. The factor secret never leaves the provider control.
- `$V password PAGE ROLE current|next LABEL [OCCURRENCE]` fills the role's current password, or one generated replacement kept in private worker state. `$V password-commit ROLE` adopts the replacement after the visible save succeeds, so later `actor` sign-ins use it. The daemon's `login` command keeps the launch credentials, so use `actor` for these roles.
- `$V auth-link PAGE recovery ROLE` (or `auth-link PAGE invite` for a new synthetic address) asks the owned provider's admin API for the link the app's email would carry, navigates the named owned page to the app's `/auth/confirm` URL and prints a snapshot with the token redacted. Do not `take_snapshot` or `list_pages` while that page is still on `/auth/confirm`, including after a failed Continue; native screenshots carry no URL. Redact any snapshot that captured it before packaging.
- `$V access-request EMAIL` reads stored Access Requests for one lowercase `@example.test` address, with their Account Setup Links (no token hashes).
- `$V seed account-setup` stores one approved synthetic Access Request and Account Setup Link per class: `valid`, `claimed`, `expired`, `replaced`, `failed`, and `not-approved` (its request is still pending). It prints each class's address and link state. The raw tokens stay in private worker state; `clean-seeds` removes the rows.
- `$V mail-link PAGE EMAIL setup|auth|invitation [N]` is the real-issuance counterpart of `setup-link`: it opens a link the owned app actually sent (setup email from an approval or Organization invite, or the invitation email's `/auth/renew-invite` recovery link) through its private mail sink, with the same token-redacted snapshot. Use it for renew-invite results and setup completion, and `$V mail state` to see what was sent. Controls are in [Organization invitations](organization-invitations.md).
- `$V setup-link PAGE CLASS` navigates the named owned page to the class's `/auth/setup-account?token=` link and prints a snapshot with the token redacted. It proves link handling, not approval-email delivery. Valid and claimed links redirect to the bare `/auth/setup-account`. The other classes stay on the token URL, so use the printed snapshot and native screenshots until the page navigates away.

1. **MFA challenge.** Run `$V actor identityMfa dashboard`; the helper stops on `/auth/mfa-verify` with `Verify your code`. Capture the page. Type `000000` in Verification Code with native `fill` and press Verify: the assertive `Invalid authentication code. Try again.` shows and the page stays. Run `$V mfa-code PAGE identityMfa "Verification Code"`, submit with Enter in the field and require `/dashboard` with Organization A. In a second `actor identityMfa dashboard` context, choose the `sign out` link instead: require the public page, and navigating to `/dashboard` must return to sign-in rather than the challenge.
   - Code limit. Codes for a verified factor are limited to 10 per account in 15 minutes, whatever the address. In another `actor identityMfa dashboard` context, submit wrong codes with native `fill` and Verify. The 11th submission in the window must show `Too many authenticator codes. Please wait before trying again.` and stay on the challenge; a response with status 429 and `Retry-After` appears in `list_network_requests`. Then `mfa-code` with the current code is refused with the same message. The limit is stored in the provider, so it also blocks this actor's next sign-in until the window passes: run it last for `identityMfa`, or restart the worker. Disable MFA on Account Security shares the same per-account budget.
2. **Forgot password request.** In a public context open Sign In → Forgot password. Submit `not-an-email`: the native email check blocks it, so the server's `Enter a valid email address` is not reachable from this form. Submit `identityRecovery`'s address (`identityEmails` in `$V fixture`) and then an unknown `nobody-RUN@example.test`: each shows `Check your email` with `If an account exists for` and the entered address. The visible confirmation must not reveal whether the account exists. The owned app's mail goes to the private sink: `$V mail state` shows whether an `auth` message was produced for each address, and `$V mail fail auth` exercises a delivery failure. No email leaves the worker.
3. **Recovery link and new password.** In a fresh public context run `$V auth-link PAGE recovery identityRecovery`. Its redacted snapshot shows `Confirm your password reset` and `Continue to Password Reset`; capture a native screenshot. Click Continue with the printed UID. Require `/auth/reset-password` with New Password and Confirm New Password. Fill mismatched values first (one field via `password ... next`, the other by native `fill`): Update Password must stay disabled; record whether any message explains the mismatch. Then fill both with `$V password PAGE identityRecovery next "New Password"` and `... "Confirm New Password"`, submit and require the `Password updated` panel. It shows for about 3 seconds before the page navigates to `/dashboard`, so capture it with a snapshot taken right after the press. Run `$V password-commit identityRecovery`, sign out, and prove persistence with `$V actor identityRecovery dashboard`. Re-running the same link is impossible because the token was consumed; a second `auth-link` produces a new link. The control proves link handling, not email delivery.
4. **Invite activation and renewal.** In a fresh public context run `$V auth-link PAGE invite`; continue with `Continue to Invite Setup` and require Accept Invite's Password and Confirm Password. Native `fill` may use a run-local synthetic password here because the new address has no fixture credentials; keep it out of notes. Submit and require `Account activated`, then the dashboard without any Organization membership. Separately open Request a fresh setup link (`/auth/renew-invite`): submit an empty and malformed email for validation, then a synthetic address, and capture `Check your email`. The reply is the same for an address whose invitation grant was withdrawn, but `$V mail state` then shows no new `account-setup` message.

In a fresh public context run `$V setup-link PAGE valid`: require `Choose your password` for the class's address, with Email Address disabled. Press Check setup status and require `This setup link is ready. You can choose a password now.` with the form kept. Fill both fields with one run-local synthetic password (keep it out of notes) and submit with Set Up Account. Require `/dashboard`, which sends an account without membership to `/org/new`. `$V access-request EMAIL` must show `setup_completed_at`, `setup_user_id` and the link's `used_at`. In a fresh public context run `setup-link PAGE valid` again and require `Account setup complete` with Sign in and Reset your password. Open each remaining class in a fresh public context and capture it. `expired` (`has expired`), `replaced` (`was replaced`), `failed` (`could not finish setup`) and `not-approved` (`access it was sent for was withdrawn`) show Setup link unavailable with Request a fresh setup link. The withdrawn copy also covers a link revoked by a platform rescind and an unclaimed link whose invitation grant died; [Organization invitations](organization-invitations.md#f01-invitation-grant-liveness-11-01) drives those through real issuance. `claimed` shows `Check your setup status`. Interrupted attempts use `$V fault arm NAME` before Set Up Account, with a fresh `seed account-setup` link each time. `setup-reconcile` shows Setup needs support with a support request ID; reopening the same link offers Check setup status, which finishes the committed setup as Account setup complete. `setup-finalize` shows Check your setup status, and Check setup status after `fault restore` shows Account setup complete. `setup-finalize-lost-ack` commits and shows Account setup complete with `This setup link has already been used`. `setup-password` fails the provider account write and shows the fresh-link-required message. Read `$V access-request EMAIL` after each for `setup_completed_at` and the link's `used_at`. Completion and Check setup status are `/auth/*` POSTs and count toward the shared limit. Fill New password and Confirm new password with `next` again, submit and require `Your password is updated and other sessions have been signed out.` Run `password-commit`, then `actor identitySecurity dashboard` in a new context and open Security.     - Headers. `curl -sI ORIGIN/auth/login` must show the Content-Security-Policy with `connect-src 'self' https://vitals.vercel-insights.com` and no provider or loopback origin, plus `X-Frame-Options: DENY`, `nosniff` and HSTS. The browser has no provider client: Storage files open as navigations through `window.open`, and the MFA QR code is a `data:` image.
    - Blocked requests. Navigate each page with `navigate_page` and an `initScript` that appends each `securitypolicyviolation` event's `violatedDirective`, `blockedURI` and `sourceFile` to `sessionStorage`; read it with `evaluate_script` after the page settles. Cover Dashboard, Organization home, Personnel, Calendar, Training, Critical Tasks, Onboarding, Settings General and Members, Account Profile and Security. Require no `connect-src`, `img-src`, `frame-src` or `font-src` violation. One `script-src` report with blocked URI `eval` per Organization document is Zod's capability probe (`Function('')` inside `try`), which falls back to its non-eval parser and is expected.
    - Page data. With `evaluate_script`, fetch `location.pathname + '/__data.json'` and read `document.documentElement.outerHTML`. Neither may contain `access_token` or `refresh_token`, and `document.cookie` lists no auth cookie: the session stays in HttpOnly cookies. Save only field names and booleans, never values.
    - Unverified identity. Run `$V admission-probe notificationMember notificationOther`. The genuine session cookie must be admitted (200 on both paths) and every malformed or forged variant must get 303 to `/auth/login`; save its JSON, which withholds the genuine signature.
    - Encoded paths. From a signed-in page, POST the sign-in form to `/%61uth/login?/login` with a nonexistent `@example.test` address. It shares the `/auth/*` budget with `/auth/login`: once the window's ten POSTs are spent, it returns 429 like the plain path. Run this last, because it spends the shared sign-in budget.

## Gotchas

- Supabase TOTP is enabled only in the disposable verify provider's generated config; the repository `supabase/config.toml` still leaves it off for local development. Every other auth, signup, password and rate-limit setting stays as configured.
- The app's request hook allows 10 POSTs to `/auth/*` per 15 minutes per client address, and every owned browser context shares 127.0.0.1. Sign-ins (including `actor` and `login`), sign-outs and `/auth/confirm` Continue all count, including percent-encoded spellings of those paths; `/api/*` calls and Renew Invite (its own 5 per hour) do not. Authenticator codes have a separate durable limit of 10 per account per 15 minutes. A limited Continue shows `Too many requests. Please wait and try again.` before the action runs, so the link is not consumed. Budget the run across windows and record the 429 rather than retrying in a loop. Provider limits apply separately.
- Native `get_network_request` prints request bodies, including filled passwords and codes. Never save its output for identity forms; use `list_network_requests` for status.
- A setup-link page that stays on its token URL is also token-bearing: never `take_snapshot` or `list_pages` it until it navigates away.
- `/auth/confirm` intentionally waits for an explicit button; a link prefetch does not consume the token. A used or expired token redirects to sign-in with an invalid-link error.
- A recovery or invite session is restricted to its password page until the password is set. Leaving through `Need to exit?` ends it.
- `identitySuspended` keeps its suspension for the worker's lifetime. Platform administration's suspension journey uses its own seeded accounts and restores them through the UI.
