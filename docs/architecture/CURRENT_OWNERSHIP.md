# Current capability ownership

This is the Phase 07 D01 ownership ledger for the surviving v1 application. The [baseline M01–M17 inventory](../stabilization/BASELINE.md#inventory-and-ownership-baseline) is accepted historical audit evidence: its file counts and removed-product references describe the earlier checkout. This ledger uses the current Phase 07 checkout. The [Phase 06 target archive](../stabilization/phase-06/schema-target-snapshots.md) and its fresh/upgrade proof describe a local effective target schema, not the uninspected hosted database.

## Capability and consumer census

Each row names the owner of the current capability, even when its code is still in routes or central `src/lib/server` use cases and adapters. The source anchors are representative current implementation and consumer entry points, not a claim that every import already follows the target boundary. Persisted tables, permission keys, jobs, stores and provider/SQL bindings receive their object-level disposition in the next D01 leaf, 07-01b. D01 must finish that disposition before this ledger is the complete ownership contract.

Billing and Duty Roster have no surviving application module or capability owner. Their removed runtime and active-schema identities are historical migration and verification records, not candidate public interfaces. Current `src/features/` contains nine directories: `calendar`, `critical-tasks`, `dashboard`, `groups`, `onboarding`, `personnel`, `rating-scheme`, `sign-in-rosters` and `training`. This count is a Phase 07 source observation; it does not overwrite the baseline's earlier inventory.

**Unresolved legacy endpoint:** `src/routes/org/[orgId]/api/units/+server.ts` still writes `units` using `personnel.manageUnits`. The Phase 06 local target catalog has no `public.units` relation, and a maintained-source search found no caller outside the route and its tests. This is an orphan candidate with a broken current boundary, not an intentional supported interface. 07-01b must classify the effective permission/table facts; 08-M04 must then remove the route/policy if that orphan status is confirmed. Its presence is not accepted drift.

## Observed dependency pressure

- Dashboard currently imports Calendar and Training mutable stores in `src/features/dashboard/dashboardWorkspaceHydration.svelte.ts`; its screen read model also reads Calendar stores and Rating Scheme calculations. Dashboard owns the composition, while those source owners retain data and policy.
- Onboarding currently imports Training store/types and scoped roster data in `src/features/onboarding/onboardingWorkspaceHydration.svelte.ts`. Training and Personnel remain the source owners.
- Server feature entry points still reach central `src/lib/server/core/ports.ts`, `src/lib/server/adapters/httpAdapter.ts` and central entities, for example `src/features/rating-scheme/server/ratingSchemeWorkspaceBootstrap.ts`. This is current placement, not evidence that the target public/server boundary exists.
- Routes deep-import feature contexts, stores, components and server bootstraps, for example `src/routes/org/[orgId]/calendar/+page.svelte` and `+layout.server.ts`. The D01 contract and D02 checker must distinguish legitimate delivery imports from private cross-owner imports; this inventory does not enforce either yet.
