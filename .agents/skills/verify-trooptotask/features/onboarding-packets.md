# Onboarding packets, progress and history

An Organization member starts a Person's Onboarding checklist, records progress and notes, and retains completed or cancelled packets. Onboarding authority is independent of Personnel and Training; each packet inherits its Person's Organization and Group scope.

## Sub-features

- `start`: select an existing Person and configured template, preserve the chosen date, snapshot the steps, and prevent another active packet for that Person. Authorized Personnel creation is a separate operation through Add Person.
- `progress`: toggle checkbox steps, advance or reverse paperwork stages, retain attributed notes, and derive Training completion from the owned Training source.
- `lifecycle-and-history`: cancel, reopen and complete packets, including the explicit warning for incomplete steps; retain packet/progress identities and inspect history after reload.
- `reconciliation`: explicitly resync changed definitions or switch templates, preserving completed work/notes and inactive removed steps; assigning a template to a legacy packet is a separate case.
- `scope-and-recovery`: view cannot mutate; operate manages scoped packets; configure additionally reconciles templates. Empty scope and foreign-to-target actors cannot read or change packets. Failed actions require visible feedback, retained drafts/state and usable retry; a late A response must not enter B.

## How to get to it (user POV)

Choose Onboard in Organization navigation. Use Start Onboarding to select a member, start date and template. Open a packet card to record checklist progress, resync or switch its template, cancel it or complete it. The current Kanban detail has no note editor; retained notes are visible in History. Note creation remains a supported authenticated API operation. Choose History to inspect retained packets. Reopening is currently supported by the authenticated packet API, without a visible History control. Templates opens the separate configuration workflow.

## Gotchas

- Feature entry, card labels and closed dialogs do not establish persistence or permission. Compare actual packet/progress IDs, values and ordinary authenticated response statuses.
- Network `onboarding-steps` and `onboarding-resync` controls reload before adapter creation; arm before opening a draft. `onboarding` uses the current page. Client503/held-response proof does not establish a multiwrite provider transaction or concurrency guarantee.
- Completing with incomplete steps is intentionally supported with warning and an audit count. Training completion is source-derived; preserve that distinction from manual checkbox and paperwork progress.
- Completed packet snapshots survive template edits/deletion. Do not automatically resync history or confuse a template definition with its saved progress snapshot.
- Retention cutoff, deletion counts, permissions and provider failure require separate service/SQL proof. UI history is not proof of retention and source inspection is not live evidence.
- Existing lifecycle/query/progress/resync/retention, route, store, interaction and SQL `onboarding_workflow_rls.sql` checks own distinct lower-level behavior. Reuse them; this recipe does not restore the retired browser-spec framework.
- Restore network/feedback controls and original editable fields, clean helper seeds, finish final doctor/owned cleanup and package artifacts only after the run. A failed expectation remains a failure until matching repaired proof exists.
