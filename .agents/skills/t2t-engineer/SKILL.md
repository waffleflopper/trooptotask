# Engineer TroopToTask changes

Pick the mode that answers the request. [Operating rules](../../../docs/agents/operating-rules.md), [retained contracts](../../../docs/stabilization/BASELINE.md#retained-contracts) and the [Definition of Done](../../../docs/architecture/DEFINITION_OF_DONE.md#required-commands) own project gates. The current request sets scope; this skill adds no publication, merge, deployment, message or database authority. [t2t-stabilize](../t2t-stabilize/SKILL.md) coordinates ordinary issue continuation through review and owner merge; [verify-trooptotask](../verify-trooptotask/SKILL.md) is the authoritative app-verification skill and is reached directly from this workflow.

- **Understand or investigate:** Trace the user-visible symptom through its route, feature owner, server policy, provider boundary and relevant history. Reproduce at the cheapest stable surface. Separate observations, source-supported explanations and inference. Return a falsifiable problem statement and the evidence that would disprove it.
- **Establish the affected baseline:** Derive expected outcomes from issue acceptance and approved contracts, then read the relevant [feature recipes](../verify-trooptotask/features/README.md) and existing lower-level tests. Correct or extend missing instructions, fixture roles and small reusable controls before the affected cutover; this is part of the worker's assignment. Drive the affected behavior and dependencies on the unchanged app with verify-trooptotask, including relevant failure, access and persistence paths. Preserve meaningful unit/integration/SQL tests. Direct authenticated API/SQL proof stays separately identified and does not substitute for UI interaction. A bug fix may start from a failing reproduction; a refactor requires its affected baseline to pass. Reproduce and repair authorized baseline defects, or identify their owner/dependency; never adopt a defect as the expected result. Escalate genuine product ambiguity or missing authority, not missing recipes or helpers.
- **Architect or prototype when uncertain:** For a consequential module seam, sketch caller use, types and ownership before implementation. Use a disposable prototype to settle a real behavior, interaction or performance choice. Choose the simplest shape that preserves retained contracts and discard the prototype. Routine edits need no design arena.
- **Implement the scoped change:** Change the owner and affected consumers together and remove obsolete paths in the same slice. Prefer narrow interfaces; consider request count, payload size and feedback latency. Keep approved expectations stable through a refactor. An approved behavior change updates its contract, feature recipe and relevant lower-level tests together.
- **Verify and arrange independent acceptance:** Repeat affected live verification and applicable repository checks on the final candidate. Record code version, environment, role, actual actions, expected/observed results and sanitized artifacts that survive cleanup; separate baseline, final, failed and unrun paths. For intermediate PRs, apply [scoped acceptance](../t2t-stabilize/SKILL.md#bound-the-pr-without-shrinking-the-issue), keeping the issue remainder and failures visible. Independent acceptance reviews the complete diff, requirements, direct/reverse consumers, chosen feature coverage and evidence. An available isolated reviewer may execute live paths; artifact review is not independent execution, and using the same model is not model diversity. A convenient Group save does not establish Calendar partial failure or Organization isolation. Routine work covers affected features and dependencies; full-map source/live maintenance is a separately requested upkeep pass.
- **Prepare a PR:** Inspect the final diff for intent, security, consumers, performance and unrelated edits. Record checks and material limits against the exact candidate. Explain resulting behavior and provide a short review path through important files. Seek findings with concrete failures and evidence, not speculative suggestions. Use the coordinator's proportional CodeRabbit and installed finish-pr flow when continuing an issue; respect publication and owner-merge boundaries.
- **Close a phase when authorized:** Establish all declared acceptance on the integrated result. Retain one current record with exact code references and unresolved obligations. Earlier evidence, missing live observations or an open PR cannot complete a phase. A completed issue does not authorize the next issue or phase.

For useful authorized parallel work, the coordinator owns scope, shared contracts, integration and final acceptance. Use at most two bounded workers on isolated branches/worktrees and separate `verify:app --worker 1|2` services when driving. Each brief names one outcome, exclusive files/services, preserved behavior, checks and evidence to return. Different feature files can have different owners; coordinate shared controls/fixtures and mutable services explicitly, with one driver per browser and executable inputs frozen during proof. Reconcile results before the PR boundary; workers do not independently expand scope or publish overlapping PRs. Read-only source/review work needs no browser. A short task stays local, and no particular model family or Cursor-only capability is required. After failure, fix the identified cause and repeat affected checks; persistent environment failure remains unavailable evidence rather than an endless retry loop.
