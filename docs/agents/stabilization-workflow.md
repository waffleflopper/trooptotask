# Stabilization Workflow

Use this guide for a stabilization task, phase activation or the next-task driver. Read the active task in [TODO](../stabilization/TODO.md), relevant [retained contracts](../stabilization/BASELINE.md#retained-contracts), [program decisions](../architecture/ARCHITECTURE.md#stabilization-decisions) and acceptance [evidence](../stabilization/EVIDENCE.md). General execution rules live in [operating rules](operating-rules.md).

## Checkpoints

For activation or each next-task invocation, read [workflow #1275](https://github.com/waffleflopper/trooptotask/issues/1275), the active phase parent/child and relevant comments. Reconcile [TODO](../stabilization/TODO.md), relevant [evidence](../stabilization/EVIDENCE.md), [program decisions](../architecture/ARCHITECTURE.md#stabilization-decisions), repository/default branch, local edits and actual open/closed PR state before choosing work. Recover stale metadata from verified issue mappings/PRs; record BLOCKED when uncertainty prevents verified advancement. A separate docs/tooling request does not advance the queue.

- **Activation:** Verify preceding-phase acceptance and merged changes on fetched default content; checkboxes or closed issues alone do not suffice. Reconcile native children/milestone and map every actionable phase task. Start the first deliverable on a safe new local branch from current verified default content, preserving existing branches/unrelated edits. Carry small planning/instruction edits with that deliverable's PR. Record READY and STOP before implementation.
- **Phase 07 onward:** Reconcile unstarted planning with the current September 23 boundaries in [#1275](https://github.com/waffleflopper/trooptotask/issues/1275) and the selected phase parent. Current Supabase Auth, membership, identifiers and security/data guarantees remain authoritative. Owned current provider adapters, SQL and deliberately supported retained interfaces belong in the design; abandoned internal paths belong to their cutover tasks. Future Clerk, native-client, offline, billing, universal-UI, monorepo and general API/SDK work is outside these phases. A failed current boundary blocks acceptance; absent future functionality does not. For phase 07, put substantive canonical architecture/module/identity-SQL/UI reconciliation in its foundation child and keep activation edits as planning only.
- **READY / IMPLEMENTING:** Use [t2t-engineer](../../.agents/skills/t2t-engineer/SKILL.md) to finish the active issue's fixed outcome through its necessary bounded steps. Establish affected intended behavior and coverage from issue acceptance and approved contracts first. Follow the [coverage-first gate](../../.agents/skills/t2t-verify/references/coverage-first.md): reuse or add missing fixtures/checks, prove the complete unchanged-application baseline before a refactor, then cut over all affected callers and remove replaced paths. An approved bug fix may begin with a failing reproduction; an existing defect cannot become a passing refactor baseline. Collect fresh final proof with [t2t-verify](../../.agents/skills/t2t-verify/SKILL.md), run `check-claims` with every required current receipt alongside other gates, and have independent review check both requirement completeness and results. Maintain concise TODO/EVIDENCE under the [recording contract](../architecture/DEFINITION_OF_DONE.md#recording-evidence). Local steps organize work; they are not mandatory one-leaf stops.
- **PR boundary:** Review every mapped requirement and the full candidate diff. One issue may need several independently reviewable PRs; intermediate PRs use `Refs #<child>` and keep the issue open. Only the final PR meeting complete issue acceptance uses `Closes #<child>`; never close the phase parent from a PR. Record AWAITING_PR with title/body, base/head, verification/deletions, one proportional independent review disposition, unresolved findings, release obligations and exact owner commands. Publication remains separately authorized. Stop at this boundary rather than starting another issue implicitly.
- **AWAITING_PR / AWAITING_MERGE:** Verify actual repository/head/base and child links across open/closed PRs. No PR or an open PR means report the checkpoint and STOP; review fixes stay within this child and require an explicit request. A closed-unmerged PR, failed/cancelled required verification, ambiguous linkage or manually closed issue cannot unlock advancement. Observed PR numbers alone need no documentation-only commit.
- **Verified merge:** Confirm merge to the default branch, required verification/review status and the merged result in freshly fetched default content, accounting for squash/rebase. Reconcile acceptance and child state; an intermediate merge does not complete the issue. Integrate PRs against updated main one at a time. Changed code requires affected verification; reuse applicable exact-candidate Depot evidence. Safely branch authorized continuation from updated default in a clean worktree without discarding local/unpushed edits. Carry merge evidence with normal work; never infer phase activation or publication permission.
- **All children merged:** Enter PHASE_CHECK on the integrated candidate. Record necessary repairs as bounded children with ordinary PR checkpoints. Compact completed phases into acceptance summaries with exact committed references, preserving schema/security evidence and performance baselines. Only verified phase-wide acceptance permits a candidate-SHA/evidence summary and parent/milestone closure; recover partial closure idempotently. STOP and report the next activation command; never activate another phase automatically.

Preserve verification guards, scan paths and budgets: no allowlists, skipped tests, weakened assertions or hidden failures. Use the maintained DevTools control toolkit for scoped live proof; do not restore the retired repository browser-spec suite or a runtime bypass. [Bounded tracker writes](issue-tracker.md) are authorized by explicit phase activation; Git publication/merge, production/remote actions, live data and deployment remain separately protected. Safe fetch/local branching is allowed; never force-reset, force-push, silently stash or discard work. Root data protections and the canonical isolated database contract remain unchanged.

## Bounded parallel work

After the selected application pilot is accepted and merged, authorize at most two dependency-ready workers with fixed outcomes, exclusive files, separate worktrees and separate `--worker 1|2` services. The coordinator owns shared claim/fixture/Feature Map files, module manifests, contracts, TODO/EVIDENCE and central request wiring; integrate shared changes before dependent workers consume them. Freeze shared executable inputs during proof. Check actual runner and mutable-service capacity, not model budget. The toolkit `self-test` requires idle workers and never runs alongside active verification. Integrate one PR at a time and reverify affected behavior after base changes. A worker cannot independently expand scope, publish, merge or activate a phase.

Every handoff reports phase/active child, completed local task, state, changed/deleted scope, actual checks/blockers, PR status and exact next owner action (or repeat the driver when appropriate). Flag whether push/merge appears to trigger deployment or remote migration from repository configuration, and identify unknown external settings. Owner notice, backups and app/schema compatibility must precede a merge that releases destructive/removal behavior; waiting for phase 15 does not prevent automatic deployment.
