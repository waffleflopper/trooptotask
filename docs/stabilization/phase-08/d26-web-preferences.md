# D26 browser preference ownership

This intermediate deliverable for [#1374](https://github.com/waffleflopper/trooptotask/issues/1374) completes the Identity portable/browser preference owner and both Training and Calendar consumers. It groups #1420's preference-triggered workspace reload, lost visible intent during navigation and stale feedback under the same state/lifetime repair. No migration is planned.

Acceptance requires immediate visible filtering, debounced serial persistence, latest local intent over older acknowledgements, visible active-save failure and explicit retry, same-Organization navigation without resetting choices, and retirement of pending work/feedback when the user or Organization changes. Successful preference-only saves must cause no workspace invalidation. The old model/queue and all consumers are removed together, without compatibility exports or boundary exceptions.

This is an independent outcome: the preference owner and both writers share one state mechanism and verification. Complete AppShell server/navigation/context ownership has different consumers and remains a subsequent cohesive deliverable. Deferred header races, remaining OrgContext consumers, Getting Started support ownership/removals and final integrated acceptance remain open; this PR cannot close #1374.

## Implementation and early checks

Identity owns the portable model and full acknowledgement schema, a per-provider debounced serial writer, initial-seed-only reactive state and its context/provider. The Organization layout uses a stable admitted user/Organization key around route children. Training and Calendar inject their narrow save ports; Training preserves its context across revalidation, and Calendar reads the owned display projection, including synchronous initial application. Both fire-and-forget callers use owner-only active-batch feedback. Destruction cancels undispatched saves and ignores late results; already-dispatched writes may persist. Full reload or a new scope reads a new server seed. This deliberately does not automatically adopt another tab's preference changes during the current lifetime.
