# Continue stabilization to the next PR

Own the selected issue through the next complete, reviewable PR. Read the [stabilization workflow](../../../docs/agents/stabilization-workflow.md) and current [#1275](https://github.com/waffleflopper/trooptotask/issues/1275); they own phase dependencies, safety, checkpoints and release rules. Use [t2t-engineer](../t2t-engineer/SKILL.md) for engineering and independent acceptance, [t2t-verify](../t2t-verify/SKILL.md) for coverage and behavioral proof, and the installed **finish-pr** skill for PR feedback and current-head checks. Locate and read finish-pr from the session's skill catalog; keep its implementation there.

“Continue #1352 through its next verified PR. You may publish; I’ll merge” includes the necessary claim/check work, authorized baseline repairs, implementation, review fixes and publication of that PR. It supplies the explicit review-fix request required by the workflow's open-PR checkpoint. Carry that authorization through the invocation instead of stopping to ask for each stage. Stop for Robert's review and merge. A narrower request keeps its narrower scope; this skill grants no additional publication, communication, tracker, merge, deployment or database authority. Phase activation and another issue require their own authorization.

## Reconcile before selecting work

Read the selected issue, parent, relevant comments, [TODO](../../../docs/stabilization/TODO.md), relevant [EVIDENCE](../../../docs/stabilization/EVIDENCE.md), retained contracts and program decisions reached through the workflow. Compare these with local branches/worktrees and dirty or unpushed work, fetched default content, and actual open, closed-unmerged and merged PRs. Use existing Git/`gh` reads with pagination, verified repository/head/base and issue links; title search alone is insufficient. Account for squash/rebase integration. Inspect review threads and exact-head CI when an open PR exists. Register each PR actually worked on with T3's `link_pull_request` when available; check thread links before handoff.

Recover stale metadata from evidence. A closed issue, checked task, green CI badge or recorded PR number cannot establish completion. Classify every remaining acceptance requirement as delivered with applicable evidence, required for this PR, or remaining after it, retaining failed/unavailable results and their owners. Resolve competing branches or ambiguous identity before dependent edits; preserve ongoing work. End reconciliation with the current stage, intended PR scope, issue remainder and available authorization clear.

## Select the next stage

Stages are decisions within the existing checkpoint, not another persisted state machine. Reassess after new evidence or a merge.

Coverage work can be its own complete PR.                                                    |

## Bound the PR without shrinking the issue

Choose the smallest cohesive result worth reviewing: complete coverage, a reproduced baseline repair, or a complete owned seam and its affected consumers. Declare its acceptance and exclusions before edits. Map every whole-issue requirement to delivered, this PR, or remaining in the existing task artifacts; use the PR body for its review scope. Keep progress in TODO/EVIDENCE and claims beside their owning task. No additional ledger, queue or duplicate claim collection.

**PR complete** means its declared outcome and all affected consumers are finished, its required candidate-bound checks and behavioral proof pass, and consequential review findings are resolved. **Issue complete** additionally requires every issue acceptance item, consumer/removal obligation and required evidence to pass on the integrated result, with all necessary PRs merged. A final PR awaiting merge is ready to complete the issue, not an already completed issue.

Intermediate acceptance applies to the declared PR scope; t2t-engineer's whole-issue completeness review still accounts for every remaining requirement. Keep the authoritative issue claim set intact. If a smaller PR needs a scoped proof set, derive its exact required entries for a temporary check input, recording selection and rationale in the existing evidence; never remove a failed requirement from the issue set. Checkers do not establish that this selection is sufficient: independent acceptance must assess direct and reverse consumers and all affected behavior. The complete baseline required by the affected refactor and complete final issue proof remain mandatory at their gates.

A coverage-only PR may deliver functioning checks that truthfully expose a product failure. Declare that outcome before claiming acceptance; keep the failing observation visible, the issue open and the dependent refactor blocked. A repair PR must prove its repaired behavior; a refactor PR cannot exclude a failure in its affected contract. Passing CI does not override failed behavioral proof, and redefining scope after a failed check cannot turn that failure into success.

Use `Refs #<issue>` for intermediate PRs. Only a final PR satisfying all pre-merge acceptance, with authorized closure on merge, uses `Closes #<issue>`; never close the phase parent from a PR. Check the entire PR title/body and included commit messages for unintended closing references before publication.

If an intermediate merge prematurely closed the issue, compare remaining requirements and failures with the merged diff and fetched default. Under existing [tracker permissions](../../../docs/agents/issue-tracker.md), reopen the unfinished child and correct misleading completion/dependency state, preserving human edits; read back the result. Publication alone is not phase activation or blanket tracker authority. Without the needed authority or access, prepare the exact correction and report that blocker while continuing independent authorized work. Neither the premature closure nor the intermediate merge unlocks dependents. Reuse an existing correction rather than repeatedly commenting. Likewise, close a genuinely finished but open issue only with verified integrated acceptance and applicable tracker authority.

## Verify, review and finish

Arrange an acceptance pass independent of implementation: give the reviewer the declared PR scope, full issue requirements/remainder, complete diff and actual evidence. Ask whether required behaviors and consumers are covered and whether the results prove them. An available independent runner may execute verification under the existing isolation rules; a review of receipts must not be reported as independent live execution. Missing independent acceptance remains visible rather than silently becoming a self-review pass.

Use CodeRabbit for the intended diff. Inspect installed CLI help and existing review results first; specify the actual base and committed/uncommitted scope so committed PR work is included. Record reviewed base/head or patch, scope and consequential dispositions in the existing work record. Reuse a completed review for unchanged material. Fix actionable findings and reverify affected behavior; request another review only for changed material or consequential unresolved uncertainty. Optional suggestions are not acceptance gates. A pending, rate-limited or unavailable review is not a clean result; use bounded retries and report the missing review without an endless “zero suggestions” loop.

Apply the [Definition of Done](../../../docs/architecture/DEFINITION_OF_DONE.md#required-commands) for the actual change and use **finish-pr** through the authorized stopping point. It owns paginated feedback handling, permitted replies/resolutions and current-head CI. Reuse applicable exact-candidate [Depot evidence](../../../docs/ci.md); distinguish a runner's unsupported check API from actual CI failure and use available read-only host/Depot results. If results cannot be observed, leave them unavailable. Publication can occur with checks pending when authorized, but label the PR unverified until required checks and requested reviews finish. CodeRabbit success does not replace behavioral or independent acceptance evidence.

Fix in-scope review failures without another request. Changes after review/proof need affected reverification; new PR heads need current-head CI. Stop when the PR is complete or a concrete blocker prevents completion within available authority/capabilities. Never merge on Robert's behalf under this invocation.

## Parallel work and handoff

For explicitly authorized parallel workers, apply the workflow's [bounded parallel rules](../../../docs/agents/stabilization-workflow.md#bounded-parallel-work) and t2t-engineer's worker briefs. Verify the accepted application-pilot prerequisite, exclusive files/worktrees/services and actual capacity before launch. Keep shared claims, fixtures, Feature Map, contracts, manifests, TODO/EVIDENCE and integration with the coordinator; freeze executable inputs during proof and integrate one PR at a time. Independent read-only review does not activate parallel application workers. No new scheduler or orchestration framework is needed.

Every handoff names the phase/issue and existing checkpoint, PR URL/base/head, what this PR completes, whether the issue is finished, remaining requirements/failures and their owners, actual checks/review disposition, release obligations and Robert's next action. For a verified PR: “Review and merge this PR; then repeat the continuation request” if issue work remains. For a blocker: name the precise decision, permission or unavailable capability instead of asking Robert to rediscover the workflow. Inspect publication/deployment configuration and disclose unknown external settings under the workflow's release rules.

When changing this skill, exercise [the decision fixtures](references/decision-fixtures.md) with an independent reader and no live mutations. Record outcomes in the tooling PR, not stabilization progress.
