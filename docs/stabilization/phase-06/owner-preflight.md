# Phase 06 owner preflight and failure path

Phase 06 D01 [#1328](https://github.com/waffleflopper/trooptotask/issues/1328) supplies the pre-retirement [effective catalog](replay-catalog.md), [dependency classification](dependency-classification.md), [synthetic Calendar contract](calendar-provenance-fixture.md) and [read-only candidate report](owner-candidate-report.sql). D02 owns the forward migration, complete Calendar/rank detachment and fresh/populated-upgrade proof; D03 owns any separately proved generated-type disposition and integrated release verification. D01 has made no destructive change. A local replay match is not evidence about the hosted target.

## Private hosted candidate report

Only a separately authorized owner may select a hosted target and run the SQL. The owner first confirms the target project and migration ledger, uses a role with full RLS visibility and `SELECT` on every required table, and keeps the output private. The file is for `psql` because it contains `\set ON_ERROR_STOP`; do not paste it into SQL Editor unchanged. A placeholder invocation is:

```bash
psql 'service=OWNER_APPROVED_TARGET' -X -v ON_ERROR_STOP=1 \
  -f docs/stabilization/phase-06/owner-candidate-report.sql
```

The report uses a read-only, repeatable-read transaction with bounded lock and statement timeouts. It refuses a missing Phase 05 archive migration, required relation/column, table read grant or full RLS visibility. It returns exact row counts for all 14 Duty tables; one line per **every** Calendar assignment type with its Organization/type IDs, saved-assignment count, old run/date-lineage counts and surviving template/history link counts; totals for saved assignments, types, Sign-In Rosters, statuses and Organizations; and the latest migration version/count. It emits no names, Personnel records or assignment payloads. Even IDs and counts are private operational evidence, not content to commit or post to GitHub.

This is a **candidate report**, not a complete hosted catalog assertion. The owner must compare the actual effective hosted relations, constraints, indexes, policies, grants, function overloads/bodies, triggers, dependencies, cron/publication state and migration ledger against the [classified local catalog](dependency-classification.md), using an approved private capture with sufficient visibility. Do not run the full local catalog query against hosted data without a separate private evidence plan: it can print routine bodies and job commands. The current fixture has nine saved assignments, five types and three Sign-In Rosters; those are synthetic examples, never expected hosted counts.

Template/history links establish only a surviving relationship. Missing links can follow old deletion or `ON DELETE SET NULL`; run/date lineage can be incomplete, inconsistent or manually edited. A type's name, zero saved slots, old link or absence of a link cannot prove it was created by Duty Roster. D02 preserves **every** assignment/type row and current label by default, including unreferenced types. D03 may consider a targeted disposition only after independent provenance and separate authorization. The report cannot identify external callers, prove a backup can restore, or certify app/schema compatibility.

Before the source relations disappear, the owner must also preserve a **private, exact provenance capture** for D03: every assignment type's ID, Organization ID, current label/settings; every saved assignment's ID, Organization ID, type ID, date, assignee, creation time and old run/row-date lineage; every `duty_roster_templates` template ID, Organization ID and type ID; every `duty_roster_template_runs` run ID, Organization ID, template ID, dates and snapshot payload; and every `duty_roster_history` history ID, Organization ID and type ID. Keep the relevant old source rows needed to explain a candidate's creation, reuse or later edit in restricted owner evidence, with capture time, target and file hashes. Compare run/template/type/Organization links and snapshots to **saved** assignments; the saved values win when they differ. Aggregate counts from the candidate report and a backup that has not been made reviewable are insufficient for D03's later classification. Do not post these rows or payloads to GitHub. Missing or inconsistent lineage leaves that type **unresolved and retained**; it cannot become a deletion candidate from a name or zero slot count.

## Stop conditions and owner sequence

1. Before any D02 releasing publication or merge, record its **reviewed candidate/head SHA**, migration file/hash, target project, applied migration ledger and currently deployed no-Duty app SHA privately. Verify the no-Duty app is running against the old schema, and drain old Duty-dependent instances, workers, in-flight requests, direct URL callers and external jobs. Repository `vercel.json` has no Duty cron, but external schedules are unknown. Publication/merge can trigger Vercel; verify external deployment and migration triggers and user notice before a releasing action.
2. Arrange a backup/PITR point and **tested restore** covering schema/data, Auth, Storage and relevant configuration. Decide how writes after the restore point will be reconciled and which app version can operate after retirement. An old Duty-dependent binary is unsafe after destructive commit. Keep private restore receipts.
3. Capture the hosted catalog, exact private provenance described above and retained data/permission baseline **before** any schema retirement. Run the candidate report only with full visibility and review all output. Preserve exact Calendar assignment/type IDs, Organization, date, assignee, scope, current labels/settings and independent Sign-In/Personnel facts for later comparison. A partial result, timeout, missing privilege, schema/ledger drift, unclassified dependency, unknown external caller or ambiguous row provenance is **BLOCKED** for the affected destructive operation. Investigate and amend the reviewed cutover; do not suppress an assertion, infer empty data from an RLS-filtered result, delete by label or apply a broad cascade.
4. Review D02's one complete forward migration, tests, generated artifacts and actual fresh/populated-upgrade proof against this D01 baseline. Its migration must recheck dependencies and abort atomically on mismatch before dropping any Duty object; D01's read-only snapshot cannot freeze later changes. After a separately authorized D02 merge, record its **actual merge SHA** and verify the deployed compatible app and unchanged pre-retirement target before a separately authorized hosted migration. Recheck that no external automation applied the migration during merge. The app, caller, backup, data and compatibility preflights must pass before any destructive release. This driver performs no remote SQL.
5. After a separately operated migration, compare retained Calendar identities/fields and authorized/denied Organization/Group CRUD, ranks, Sign-In Rosters, Personnel and exports against the private before-state. Confirm target catalog and ledger, then retire external Duty-only configuration/jobs. If validation fails before commit, keep callers stopped and investigate the rolled-back transaction. After commit, use a reviewed compatible roll-forward or the tested owner-operated restore, reconciling later writes and Auth/Storage/config; reverse DDL or redeploying the old app cannot recreate deleted facts.

The [release boundary](../RELEASE.md#phase-06-activation-and-release-boundary) retains these prerequisites for D02/D03. Actual hosted schema/data, deployed app, caller drain, backup/restore, external settings and future migration result are **UNVERIFIED** in D01.
