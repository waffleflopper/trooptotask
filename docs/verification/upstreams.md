## Runner and setup

Project skills live in `.agents/skills/<name>/SKILL.md`; the repository instructions link the TroopToTask workflow entry points so an existing session can read them directly. The copied pstack generator and maintenance skill remain user-invoked and use `.agents/skills/` paths. Start a fresh agent session if automatic skill discovery or MCP registration has not refreshed. The inspected runner supports delegated `gpt-6-sol` with `xhigh` effort; use that selected configuration when delegating. The coordinating session used `gpt-6-astra` with `high` effort. Neither model name is a Cursor Task or cloud-agent capability. At most two implementation workers may own separate worktrees and mutable services; research and read-only review do not become overlapping implementation lanes.

On this Linux workstation, run `npm ci`, then `npm run verify:app -- setup`. Local Docker must be running, with Python 3 and the Supabase CLI on PATH. Automatic Chrome provisioning also needs network access, `unzip`, and Chrome's operating-system libraries. `setup` reports `BLOCKED` with the missing provisioning path; it does not require a personal Chrome profile or silently install system packages. `launch` also provisions the pinned browser if no compatible installed browser exists. No hosted provider credentials or manual synthetic-user creation are needed.

Worker state lives outside the checkout in a private, checkout-specific directory; `.verification/evidence/` retains evidence after cleanup. Following compaction, reconnect with `info` and `doctor` before driving. A changed executable candidate requires `restart`; a lost supervisor requires owned `cleanup` and `launch`. These are persisted resources, not guarantees that an agent's conversation or task resumes automatically. The existing context-window and compaction settings were preserved. GitHub and Depot access were available in the implementation session; local browser proof does not require them.
